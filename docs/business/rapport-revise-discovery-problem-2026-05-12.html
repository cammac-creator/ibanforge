Erratum

Les deux rapports précédents étaient construits sur une prémisse erronée.

L'audit du 12 mai (v1) et le rapport stratégique complet (v2) supposaient implicitement que les 78 opérations facturables et les 65 clés avec crédits représentaient au moins partiellement de vrais utilisateurs externes. Sur cette base, j'ai recommandé un pivot positionnement Swiss + vIBAN avec checkpoint binaire à 90 jours et un plan d'action de 47 actions priorisées.

Tu m'as corrigé : « sauf erreur toutes les clés API générées viennent de test ». Cette donnée change la nature du problème. On ne répare pas un funnel qui n'a jamais été activé par un acheteur externe — on ne sait pas si le produit a même un acheteur.

Le diagnostic précédent était « positioning problem » : corriger le packaging, les canaux, l'outreach pour réveiller une demande latente. Le bon diagnostic est « discovery problem » : la demande latente n'a jamais été observée en 14 mois × 6 surfaces de distribution publiques. Le plan d'action change donc complètement.

4.Base rates documentés — la science du « no traction at month 14 »

Issu de la recherche externe parallèle (Indie Hackers, Failory, CB Insights, First Round, Lean B2B, Carta, Freemius, MicroConf). Chiffres réels, pas opinions.

  • 92 % des micro-SaaS meurent dans les 18 mois (RockingWeb 2025). Le sous-groupe « zéro user externe à 14 mois » est dans la partie haute de cette mortalité.
  • 42 % des startups meurent de « no market need » (CB Insights, analyse 483 post-mortems). Signal-tell #1 : absence d'interview client + absence d'user externe.
  • First Round Capital : founders qui parlent aux users hebdomadairement atteignent PMF en moyenne 9 mois ; ceux qui parlent mensuellement mettent 22 mois. Avec 0 conversation client documentée, le compteur ne démarre pas.
  • Rob Walling (MicroConf) — règle empirique : si un produit B2B n'a aucun signal externe à 12 mois (pas un user, pas un email entrant non sollicité, pas un design partner), la proba d'atteindre ramen-profitable dans les 12 mois suivants est < 5 % sans changement structurel majeur (buyer, modèle ou produit, pas wording).
  • Lean B2B (Etienne Garbugli, 24 B2B SaaS étudiés) : time-to-PMF médian B2B = 2 ans, MAIS avec alpha sorti à 1-3 mois et itération sur feedback users. Sans feedback loop, le temps écoulé ne compte pas.
  • Carta Solo Founders Report 2025 + Freemius State of Micro-SaaS 2025 : 30 % des micro-SaaS n'atteignent jamais 1 k$ MRR et sont abandonnés. La distribution est bimodale : signal précoce ou aucun signal.

Mythes à enterrer (faux « second souffle »)

Plusieurs cas sont systématiquement cités comme exemples de « persévérance qui a payé ». La recherche montre qu'aucun ne matche le profil « 0 user externe pendant 14+ mois » :

  • ConvertKit (Nathan Barry, mois 16) : ~1 330 $ MRR existant avant le « kill or double down ». Signal pré-pivot solide.
  • Plausible (Uku Täht, mois 14) : ~100 subscribers payants et 400 $ MRR avant le tournant. Slow ramp, pas zéro.
  • n8n (Jan Oberhauser) : 6 ans de build mais a levé 12 M$ Series A en 2021. Pas un solo bootstrap.
  • Pieter Levels : tue chaque projet en ~1 mois s'il n'y a pas de signal. Nomad List est son 7e essai, 9/10 projets tués vite. L'inverse de la persévérance aveugle.

Conclusion de l'étude : aucun cas documenté publiquement de solo founder à zéro user externe pendant 14+ mois ayant décollé via pivot ou via « second souffle ». Les success stories partent toutes d'au moins un signal d'usage caché.

Sorties propres — démythification

  • Open source comme bouée : Sentry, Plausible, Mautic étaient OSS dès le jour 1 OU avaient des users. Aucun cas où passer un produit en OSS au mois 14 sans user a inversé la trajectoire.
  • Acqui-hire à zéro user : Acquire.com cite Andrew Gazdecki — il faut typiquement 1 M$ ARR pour viser 3-6× ARR. En dessous, les transactions à 20-50 k$ existent surtout pour des assets avec users mesurables. Pour 0 user externe, l'asset deal réaliste est 0-5 k$ (le code), sauf si la base de données BIC enrichie (121k entrées agrégées GLEIF + SWIFT + Bundesbank + SIX + NBP + EBA + classification vIBAN) a une valeur acquéreur stratégique pour 5-20 k€ chez NetGuardians, Apiax, ou un acteur compliance CH.

5.Le plan 21 jours — Discovery pure, zéro code

Remplace les 90 jours du rapport précédent. Objectif : déterminer en 3 semaines, avec preuves empiriques, si un acheteur externe existe pour IBANforge.

7.Sorties propres — si l'issue est STOP

Pas un échec. Trois sorties professionnelles, classées par bénéfice résiduel pour toi.

Option E1 — Open source du code core (recommandé)

  • Quoi : passer la lib de validation IBAN (mod97, BBAN parsing, 75+ pays) sous licence MIT sur GitHub. Garder fermé : la base BIC enrichie (121k), la classification vIBAN/EMI (84+ mappings), le risk scoring, l'enrichissement Swiss clearing.
  • Effort : 1-2 jours pour extraire la lib, écrire un README, publier npm + PyPI.
  • Bénéfices réels : GitHub stars (10-100 attendues en 6 mois), mention dans awesome-lists CH/fintech, signal CV solide, possibilité de contacts entrants sans marketing actif.
  • Honnêteté : cela ne fera pas décoller IBANforge. La recherche montre qu'aucun cas documenté d'OSS-pivot-à-zéro-user n'a inversé une trajectoire. Mais c'est un atout permanent sur ton profil et un cadeau honorable à l'écosystème.

Option E2 — Mode rente passive

  • Quoi : garder l'API en ligne, cron de refresh data mensuel automatisé, 0 marketing actif, 1-2 h/mois de maintenance.
  • Coût : ~6 $/mois Railway + temps minimal.
  • Revenu attendu : probablement 0-20 $/mois. Sans illusion : il n'y a pas d'utilisateur externe aujourd'hui — il n'en arrivera pas demain en mode passif.
  • Bénéfice : optionalité gratuite. Si la donne change (PSR/PSD3 fait du bruit en 2027-2028, AMLR active la demande vIBAN), tu peux réactiver. Sinon, le domaine et le brand restent comme asset CV.

Option E3 — Tenter une vente d'asset (long shot)

  • Quoi : cold pitch à 5-10 acquéreurs probables, asset deal pour la base BIC enrichie + classification vIBAN + brand ibanforge.com.
  • Cibles probables : NetGuardians (CH, fraud), Apiax (CH, RegTech), Confinale (CH, RegTech), iPiD (global VoP), ComplyAdvantage (UK, AML), Trustpair (FR, IBAN monitoring), SurePay (NL, VoP).
  • Valorisation réaliste : 0-20 k€ en asset deal (code + dataset), avec espérance la plus probable autour de 5-10 k€. Pas un acqui-hire glamour. La recherche montre que les transactions Acquire.com à 30-150 k pour 0 user externe sont quasi inexistantes publiquement.
  • Effort : 10-15 h pour pitch deck + 5-10 cold emails + 2-3 calls. Cycle 4-12 semaines.
  • Honnêteté : probabilité de signer un deal < 15 %. Mais c'est gratuit à tenter pendant que la rente E2 tourne.
Verdict sorties

Ordre optimal : E1 (open source) immédiat + E2 (rente) en parallèle + E3 (cold acquéreurs) en option pendant 4-12 semaines.

Cette combinaison libère ton temps (10 h/sem) pour un projet avec signal de demande dès la semaine 1 — c'est le vrai gain. Le coût d'opportunité du temps de solo founder est l'asset le plus important à protéger.

8.À exécuter cette semaine — vérifications empiriques

5 requêtes SQL à lancer sur la prod (via dump SQLite ou endpoint admin dédié) pour solidifier le diagnostic avant les 30 interviews. Et 3 ALTER TABLE pour ne plus jamais naviguer à l'aveugle.

SQL #1 — Confirmer la composition emails

SELECT email, COUNT(*) AS n_keys, MIN(created_at) AS first, MAX(created_at) AS last
FROM api_keys
GROUP BY email
ORDER BY n_keys DESC
LIMIT 30;

Si la liste contient majoritairement example.com, admin-test-*, consume-*, stripe-buyer, credits-buyer : confirmation officielle. Si tu y trouves même 1 email corporate externe vérifiable (LinkedIn, Crunchbase), c'est un signal majeur à exploiter immédiatement.

SQL #2 — Smoking gun emails de test connus

SELECT email, COUNT(*) AS n
FROM api_keys
WHERE email LIKE '%example.com'
   OR email LIKE '%admin-test%'
   OR email LIKE '%consume-%'
   OR email LIKE '%+test%' OR email LIKE '%+staging%'
   OR email LIKE '%mailinator%' OR email LIKE '%tempmail%'
   OR email LIKE '%guerrillamail%' OR email LIKE '%10minutemail%'
GROUP BY email
ORDER BY n DESC;

SQL #3 — Retention par email (signal d'usage réel)

SELECT k.email,
       COUNT(DISTINCT DATE(r.created_at)) AS active_days,
       MIN(r.created_at) AS first_call,
       MAX(r.created_at) AS last_call,
       julianday(MAX(r.created_at)) - julianday(MIN(r.created_at)) AS span_days
FROM api_keys k
JOIN request_log r ON 1=1  -- adapter selon le join réel sur key_hash
WHERE r.status < 400
GROUP BY k.email
HAVING active_days >= 3 AND span_days >= 7
ORDER BY active_days DESC;

Cette requête isole les emails qui ont fait des appels répartis sur ≥ 7 jours. Le seuil de « ≥ 3 jours actifs sur ≥ 7 jours » distingue les tests one-shot des utilisateurs récurrents. Si la requête retourne 0 ligne : confirmation que personne n'utilise sérieusement. Si elle retourne 1-2 lignes : contacte ces emails immédiatement.

SQL #4 — Scanner / fuzzing detection

SELECT path, COUNT(*) AS hits, SUM(CASE WHEN status >= 400 THEN 1 ELSE 0 END) AS errs
FROM request_log
WHERE path LIKE '/v1/agent%' OR path LIKE '/v1/compute%'
   OR path LIKE '/v1/translate%' OR path LIKE '/v1/route%'
   OR path LIKE '/v1/data%' OR path LIKE '/v1/random%'
   OR path LIKE '/v1/nonexistent%' OR path LIKE '%demon%'
   OR path LIKE '%bic/$%' OR path LIKE '%bic/:%!!%'
GROUP BY path
ORDER BY hits DESC;

SQL #5 — Heatmap horaire (humain vs bot)

SELECT hour, COUNT(*) AS hits,
       ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1) AS pct
FROM request_log
GROUP BY hour
ORDER BY hour;

Distribution plate 24/7 → bot. Pic 8h-18h UTC (= 9h-19h CET, heures de bureau Suisse) → humain. Distribution actuelle attendue : plate avec pics ciblés sur tes propres horaires de test.

Instrumenter pour le futur — 3 ALTER TABLE

ALTER TABLE request_log ADD COLUMN ip TEXT;
ALTER TABLE request_log ADD COLUMN user_agent TEXT;
ALTER TABLE request_log ADD COLUMN asn_kind TEXT; -- 'datacenter'|'residential'|'corporate'|'unknown'

Ces 3 colonnes permettront de distinguer définitivement test/CI/scanner/externe dans tous les rapports futurs. Effort : 1 h de code (middleware Hono qui parse l'IP et le User-Agent, lookup ASN via une lib locale ou un service free comme ipinfo.io free tier).
