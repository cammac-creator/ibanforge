01 — Verdict d'ensemble

Un produit mûr, miné par la dérive entre ses surfaces.

La bonne nouvelle d'abord : aucun finding critique, le moteur de validation IBAN/BIC est exact (mod-97 BigInt conforme ISO 13616, 89 longueurs pays correctes), la sécurité de base est sérieuse (CORS durci, prepared statements partout, signature Stripe vérifiée sur le corps brut, fail-fast au boot), et l'agent-readiness est un vrai atout (MCP, x402, A2A, OpenAPI, llms.txt). Le talon d'Achille n'est pas le code métier — c'est l'absence de source unique de vérité : prix, version, nombre de pays, schémas de réponse et descriptions d'outils sont recopiés à la main sur 6+ surfaces et ont déjà divergé.

⚠ Le finding le plus dangereux Le rafraîchissement de la base de compliance peut échouer en silence : si le téléchargement OpenSanctions plante, chaque source n'émet qu'un WARNING non bloquant, la base se construit avec zéro entité sanctionnée, et l'API répond alors « propre » (bank_sanctioned: false) pour toutes les banques. Un faux négatif systémique, invisible. → Corrigé en live par une garde plancher qui refuse de publier une base sous 50 entités.

02 — Comment l'audit a été mené

Lire, pas deviner. Puis tenter de se réfuter soi-même.

Chaque finding cite une ligne de code réelle. Les 15 findings élevés sont ensuite passés par un second agent dont la seule mission était de les démolir en relisant le code — un garde-fou contre les faux positifs plausibles. Deux findings ont effectivement été écartés ainsi (honnêteté méthodologique : un prétendu bug sur iban-format.ts n'était qu'un commentaire JSDoc).

1 · Fan-out

12 auditeurs, un par sous-système & dimension, lisent le code en parallèle.

2 · Verify

Chaque finding élevé est confié à un sceptique chargé de le réfuter via le code.

3 · Synthèse

Dédup, priorisation, et tri en quick-wins sûrs vs décisions produit.

Le screening sanctions ne couvre que la banque (BIC8), jamais le bénéficiaire

Or ~99% des désignations OFAC/EU/UN visent des personnes ou sociétés, pas des banques. Présenter cela comme « sanctions screening » crée un faux sentiment de sécurité, et c'est le claim le plus exposé juridiquement.

Le prix du batch est contradictoire — il faut choisir une vérité

2 findings High
High

Batch facturé un forfait fixe de $0.20 en x402, mais $0.002/IBAN annoncé partout ailleurs

Un agent qui valide 1 IBAN via x402 paie 0.20 USDC alors que la réponse JSON lui dit avoir payé 0.002 — jusqu'à 100× trop. Et le revenu enregistré (N×0.002) ne correspond pas au montant réglé on-chain ($0.20), ce qui fausse /stats.

src/middleware/x402.ts:228 · src/routes/iban-batch.ts · openapi.ts · discovery.ts
Deux voies possibles : (a) prix x402 dynamique = N × 0.002 (aligne sur la promesse), ou (b) assumer le forfait $0.20 et corriger handler + doc + cost_usdc. Dans les deux cas, cost_usdc renvoyé doit égaler le montant réellement réglé. Ton arbitrage requis.
Pourquoi je n'ai pas poussé le renommage réseau x402 Un quick-win « network: 'base' → 'eip155:8453' » dans le document de découverte /.well-known/x402 était tentant (cohérence avec le settlement). Je l'ai retiré du lot : ce document est un contrat externe consommé par x402scan/CDP, qu'aucun test ne couvre — « cohérent » peut être « cohérent-mais-faux ». À vérifier contre la convention réelle des consommateurs x402 avant tout changement.
06 — Dette de dépendances

19 PRs Dependabot en attente · 65 alertes GitHub.

Au git push, GitHub a signalé 65 vulnérabilités sur la branche par défaut (18 hautes, 41 modérées, 6 basses) et 19 PRs Dependabot ouvertes non mergées (zod, hono, typescript-eslint, better-sqlite3, frontend React/shadcn…). Ce n'est pas bloquant aujourd'hui, mais c'est une dette qui grossit. Recommandation : traiter les PRs groupées (le dependabot.yml les regroupe déjà proprement) après un npm run check sur chacune.
