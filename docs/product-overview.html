// 01 — TL;DR

En quatre phrases.

IBANforge est une API de validation/enrichissement IBAN + BIC + Swiss clearing + compliance. Elle est consommable par humains (REST), par développeurs (SDK TypeScript & Python), et par agents IA (MCP stdio + MCP HTTP). Le paiement se fait soit via clé API gratuite (200 req/mois), soit via x402 micropaiements USDC sans compte, soit — Phase 2 — via crédits Stripe prépayés. Le produit fonctionne, mais l'acquisition client n'est pas encore prouvée : plusieurs centaines de signups générées, conversion en clients payants proche de zéro (mai 2026).

Ce qui est solide

  • API en ligne, p99 < 50ms, 0% downtime constaté
  • Couverture BIC supérieure aux concurrents low-cost (121K vs ~50K)
  • Données Swiss BC-Nummer/QR-IID — aucune autre API publique ne l'expose
  • Premier acteur à exposer une API IBAN via MCP natif
  • Premier acteur à supporter x402 (USDC sur Base L2)

Ce qui n'est pas encore prouvé

  • Aucun client payant identifié à date
  • Marché x402 actuellement quasi-nul (early adopter)
  • SEO inexistant face à IBAN.com (20 ans d'historique)
  • Stripe credits non encore implémentés (Phase 2)
  • Conversion signup → client payant proche de zéro malgré ~280 clés API générées
// 02 — Surface du produit

Quatre canaux d'accès, un seul backend.

Le même cœur (Hono + SQLite) sert quatre interfaces. L'utilisateur final choisit son canal selon son profil : un humain teste via la landing, un développeur intègre le SDK, un agent IA charge le MCP, un système autonome paie via x402.

B. Outils MCP (Model Context Protocol)

Le même backend, exposé pour les agents IA via le standard MCP. Deux modes de transport : stdio (le client lance npx ibanforge-mcp) ou Streamable HTTP (POST sur /mcp). Cinq outils, descriptions complètes côté serveur avec triggers "WHEN to use".

Outil MCP Quand l'agent l'appelle Coût
validate_iban L'utilisateur mentionne un IBAN, un compte bancaire, un virement SEPA $0.005
batch_validate_iban Liste d'IBANs, nettoyage CSV, dédup base clients, triage liste de paie $0.002/IBAN
lookup_bic L'utilisateur a déjà un BIC/SWIFT et veut l'institution, la ville, le LEI $0.003
lookup_ch_clearing BC-Nummer ou IID Suisse — la seule API qui expose ces données publiquement $0.003
check_compliance Pré-vol d'un paiement SEPA / cross-border : sanctions + FATF + VoP + risk score $0.02

// 03 — Données sous le capot

D'où viennent les 121 399 BIC ?

Toutes les données sont publiques (CC0, MIT, gratuit). Aucune licence SWIFT propriétaire — c'est à la fois une force (légalement clean) et une limite (la couverture totale du registre SWIFT officiel n'est pas atteignable sans payer SWIFT).

Répartition des 121 399 BIC par source

BIC + LEI

Sur les 121 399 BIC, seules les 38 761 entrées GLEIF contiennent un LEI (Legal Entity Identifier). Pour les 82 638 autres, le champ lei retourne null. C'est honnête : on ne peut pas inventer un LEI.

Refresh mensuel

Cron GitHub Actions (.github/workflows/refresh-bic.yml) re-télécharge GLEIF, BankMaster, Bundesbank, EBA, NBP, reconstruit la base, commit + Railway redeploy. Pas d'intervention manuelle.

Swiss BC-Nummer

Les 1 190 entrées (institutions, succursales, redirects) viennent du fichier officiel SIX BankMaster CSV. Inclut SIC, euroSIC, QR-IID, paiements instantanés CHF, classification (banque cantonale, Raiffeisen, PostFinance, etc.). Aucune autre API publique n'expose ces données.

Compliance

Sanctions OFAC SDN + EU + UN + entités sanctionnées par BIC8. FATF grey/black list. SEPA scheme participation (SCT, SCT_INST, SDD). VoP participants EBA RT1. Refresh trimestriel manuel via npm run compliance:refresh.

Émetteurs vIBAN / EMI

85 entrées dans issuers.ts classifiées en 3 types : digital_bank (12 — bunq, Monzo, N26, Revolut, Qonto, Starling…), emi (60 — Wise, Mollie, Adyen, Currencycloud…), payment_institution (13 — Stripe Europe, Modulr, Solarisbank, GoCardless, TrueLayer, LHV…). Curé manuellement à partir des registres EBA et nationaux.

Pays IBAN

84 pays avec longueur IBAN officielle, structure BBAN (positions bank_code, branch_code, account_number), zone SEPA, obligation VoP. 26 pays ont en plus un IBAN d'exemple canonique pour aide à l'agent.

Limite à connaître Le registre SWIFT officiel contient ~150 000 BIC actifs. Notre agrégation publique en couvre ~80%. Pour les 20% restants (typiquement de petites institutions exotiques), on retournera found: false. La couverture des grandes banques européennes, américaines et asiatiques est complète.
// 04 — Anatomie d'une réponse

Ce que tu reçois quand tu valides un IBAN.

Une seule requête POST /v1/iban/validate retourne 25+ champs structurés. Voici ce que chacun veut dire et à quoi un client peut s'en servir.

// POST /v1/iban/validate { "iban": "CH9300762011623852957" }
{
  "iban": "CH9300762011623852957",           // normalisé sans espaces
  "valid": true,                                  // mod-97 + structure OK
  "formatted": "CH93 0076 2011 6238 5295 7",       // pour affichage humain
  "check_digits": "93",                            // chiffres de contrôle
  "country": { "code": "CH", "name": "Switzerland" },
  "bban": {
    "bank_code": "00762",                          // IID UBS
    "branch_code": null,
    "account_number": "011623852957"
  },
  "bic": {                                              // résolu via bank_code → BIC
    "code": "UBSWCHZH80A",
    "bank_name": "UBS Switzerland AG",
    "city": "Zurich"
  },
  "sepa": {
    "member": true,
    "schemes": ["SCT", "SDD", "SCT_INST"],     // schémas dispos
    "vop_required": false                          // CH non-eurozone
  },
  "issuer": {
    "type": "bank",                                // bank | digital_bank | emi | payment_institution
    "name": "UBS Switzerland AG"
  },
  "risk_indicators": {
    "issuer_type": "bank",
    "country_risk": "standard",                    // standard | elevated | high
    "test_bic": false,                             // 8e char du BIC = 0
    "sepa_reachable": true,
    "vop_coverage": false
  },
  "clearing": {                                         // uniquement CH/LI
    "iid": "762",
    "name": "UBS Switzerland AG",
    "type": "bank",
    "town": "Zurich",
    "sic": true,                                   // participe à SIC
    "instant_payments_chf": true,                  // SIC instant CHF
    "eurosic": true,
    "qr_iid": "30762"                              // pour QR-bill suisse
  },
  "cost_usdc": 0.005,
  "processing_ms": 28.4
}

Pour qui sert chaque champ

  • valid + formatted : tous (confirmation et affichage)
  • bic : trésoreries pour SWIFT MT103/pacs.008
  • sepa : PSPs pour router vers SCT vs SCT Inst
  • issuer.type = emi : compliance pour KYB renforcé
  • risk_indicators : AML/fraud teams
  • clearing.qr_iid : éditeurs QR-Bill suisse
  • clearing.sic : routing CHF onshore

Réponse compliance en plus

L'endpoint /v1/iban/compliance ajoute :

  • sanctions : country/bank flagué OFAC, UE, UN + statut FATF
  • reachability : SEPA SCT/SDD/SCT_INST par scheme
  • vop : participant + statut (active/pending/inactive)
  • risk_score : 0-100 calculé sur 12+ règles pondérées
  • risk_level : low / medium / elevated / high / critical
  • flags : 21 valeurs possibles (sanctioned_country, fatf_grey_list, emi_issuer, test_bic…)

// 08 — Avantages compétitifs honnêtes

Vrais moats vs différenciations temporaires vs zéro moat.

L'analyse interne du 15 avril 2026 a clarifié ce qui est défendable et ce qui ne l'est pas. Cette page n'a pas vocation à se mentir.

✓ Vrais moats

  • Classification vIBAN/EMI — 85 émetteurs mappés, aucun équivalent public. Avantage : 12–18 mois.
  • Données Swiss BC-Nummer — la seule API publique qui les expose en JSON. SIX vend une licence corporate, on contourne en restant sur l'usage public.
  • Données cumulatives d'usage — chaque appel enrichit nos stats. Asymptotique mais réel.

⊖ Différenciations temporaires

  • x402 micropaiements — copiable en 2–3 mois. Marché embryonnaire aujourd'hui.
  • MCP server natif — fenêtre 12–24 mois avant que les big players (IBAN.com, SurePay) ajoutent un MCP.
  • Pricing agressif $0.005 — dépendant de notre coût marginal < $0.0001/appel. Tenu tant que SQLite + Railway suffisent.

× Zéro moat

  • Algorithme mod-97 — ISO 13616, 50 lignes de code. Public.
  • Données GLEIF — CC0 domaine public, n'importe qui peut les utiliser.
  • Brand & SEO — IBAN.com a 20 ans d'historique. On part de zéro.
  • Stack technique — Hono / SQLite / TypeScript : aucune barrière à reproduire.
Stratégie défensive Les vrais moats (vIBAN + Swiss BC-Nummer + données cumulatives) sont ceux à investir en priorité. Faire passer les 85 émetteurs vIBAN à 200+, ajouter le routing number US et l'IFSC indien, capturer les flux d'usage agents IA pendant que les big players n'ont pas encore réagi.
// 09 — Fenêtres réglementaires

Trois vagues qui forcent la décision d'achat.

Le marché IBAN/BIC ne se vend pas sur la performance ou le design. Il se vend sur la conformité forcée. Ces trois échéances ouvrent successivement des budgets.

2025-10
VoP eurozone obligatoire
2026-Q2
PSD3 trilogue UE
2027-07
VoP étendu à tout l'EEE (CH/NO/IS/LI)
2027+
AMLR vIBAN registry centralisé

VoP — Verification of Payee

Depuis octobre 2025, toute banque eurozone doit vérifier la concordance nom/IBAN avant un SCT. Étendu à tous les virements (B2B, instant) en 2026 puis hors-eurozone en juillet 2027. Driver direct du segment 1 (PSPs) et 7 (banques).

PSD3 / PSR

La 3e directive services de paiement étend VoP à tous les virements et impose des standards plus stricts sur la classification des EMI. Driver direct du segment 2 (AML) et 4 (trésoreries).

AMLR — Anti-Money Laundering Regulation

Nouveau régulateur AMLA (Frankfurt) + registre centralisé des comptes y compris vIBAN. KYC obligatoire sur émetteurs vIBAN. Driver direct du moat principal d'IBANforge (classification vIBAN).

Fraude APP — autorised push payment

$331 milliards de pertes prévues mondialement d'ici 2027 (Juniper Research). Force tous les acteurs B2C/B2B à investir dans la prévention pré-paiement. Driver indirect mais massif.

// 10 — Limites & zones grises

Ce qu'IBANforge ne fait pas (ou pas encore).

Une page objective doit aussi lister ce que le produit n'apporte pas. Cette section sert à cadrer les attentes des clients et à identifier les vrais axes d'investissement.

Couverture BIC partielle

~80% de la couverture du registre SWIFT officiel. Pour les institutions exotiques, on retourne found: false. Pas de roadmap pour atteindre 100% sans payer la licence SWIFT (~$50K/an).

Pas de validation nom/IBAN (VoP)

On indique si une banque participe à VoP. On ne fait pas la vérification nom/IBAN soi-même (ça nécessite une connexion EBA RT1 et un statut bancaire). Les concurrents SurePay/iPiD le font.

Pas de routing US ni IFSC India

Sur la roadmap Phase 4. Aujourd'hui, IBAN-only (84 pays IBAN). Les clients trésorerie qui veulent SWIFT mondial doivent compléter avec d'autres APIs.

Stripe non implémenté

Le paiement traditionnel (Phase 2) est le bloquant n°1. Sans Stripe, un dev qui n'a pas USDC sur Base ne peut pas convertir au-delà du tier gratuit.

Pas de SLA contractuel

Single Railway instance, pas de redondance. Pour Enterprise, il faudrait multi-region + monitoring contractuel + DPA RGPD signé. Phase 5 conditionnelle.

Compliance refresh manuel

Sanctions OFAC/EU/UN refresh trimestriel manuel via npm run compliance:refresh. Pas de cron auto. Risque : un BIC nouvellement sanctionné peut avoir 1–3 mois de retard.

Marché x402 quasi-nul

Innovation visionnaire mais 2–3 ans en avance sur le marché. Aujourd'hui peu d'agents ont un wallet on-chain configuré. Coinbase Agent Kit pousse mais adoption embryonnaire.

Acquisition non prouvée

Plusieurs centaines de clés API générées mais conversion en clients payants proche de zéro à mai 2026. Hypothèse à valider : produit B2B déguisé en self-serve. Recommandation : 10–15 conversations 1:1 avec PSPs/fintechs Suisse pour confirmer.

Conclusion d'auto-diagnostic Le produit est techniquement solide mais l'acquisition reste à prouver. La priorité actionnable est (1) implémenter Stripe pour débloquer 99,9% des devs, et (2) faire 10–15 conversations 1:1 avec des prospects Suisse pour valider quel segment achète vraiment. Tout le reste (SEO, MCP listings, awesome-lists) est secondaire tant que la conversion n'est pas comprise.
