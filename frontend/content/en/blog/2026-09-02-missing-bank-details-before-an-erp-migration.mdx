*Updated 4 November 2026.*

An ERP migration is a useful moment to review supplier bank details: a target system may need fields that the old one left empty, and an export may carry typing errors or outdated bank codes. The aim is a reviewable import proposal, not an automatic replacement of bank accounts.

This recipe is for ERP integrators and finance teams preparing that review. It uses the [batch endpoint](/docs/iban-batch), keeps the source file intact and separates missing information from a failed check. For a one-off check without Python, start with the [file audit](/audit).

## Which question does each field answer?

1. **Does the IBAN have the expected structure and checksum?** `valid`. A structurally valid number is not proof that an account exists.

2. **Does a source identify the bank-code holder?** `bank_code_check`, `bank_code_holder`. An absence is decisive only when the response explicitly reports an unallocated code from an authoritative register.

3. **Where does the BIC pairing come from?** `bic.basis`, `bic.authoritative`, `bic.source`. A directory or curated-map match is not the same evidence as a register pairing.

4. **Did a national check-digit test fail?** `checks.national_check_digits`. This is separate from the IBAN checksum and is not available for every country.

5. **What is known about SEPA reachability?** `sepa.bank_reachability` and the bank's scheme results. Country-level `sepa.member` and `sepa.schemes` do not establish account reachability.

Keep the returned sources, credits and dates with the review. In particular, `as_of` dates the imported reference data; where `source_as_of` is present, it gives an older content date. Neither should be silently presented as a live bank confirmation. The [response reference](/docs/iban-validate) describes these fields.

## Three review outcomes

**Ask the supplier.** An invalid IBAN, a failed national check-digit test, or `reason: "not_allocated"` alongside an authoritative `not_in_register` verdict needs clarification. First check the export and data-entry process. Confirm changed bank details through a contact channel already known to your organisation.

**Review the evidence.** Keep missing IBANs, retired codes, unavailable lookups, partial-source misses and conflicting existing BICs in a review queue. An unknown result is not approval and is not rejection. A `superseded_by` code may describe a bank's successor; never substitute it into an IBAN or assume that it identifies the supplier's current account.

**Propose missing fields.** The example proposes a BIC or bank name only when a national register supports both the bank-code verdict and the BIC pairing, source dates are present, and no existing BIC conflicts. It leaves existing values intact. This conservative choice may leave useful partial-register results for manual review. **A proposal is not payment authorisation.** Review the source dates, the ERP's field requirements and your own approval process before importing anything.

## Download the example

[Download prepare-vendor-review-v1.py](/examples/prepare-vendor-review-v1.py). It uses Python 3.9 or later and its standard library, with no package installation.

The input is a comma-separated UTF-8 CSV with a column named `iban`. Optional `bic` and `bank_name` columns let it detect an existing BIC and avoid replacing populated names. Other columns stay in the local output. Only the IBAN column is sent to the API.

Provide your API key through the `IBANFORGE_API_KEY` environment variable, as described in [API keys](/docs/api-keys), then run:

```bash
python3 prepare-vendor-review-v1.py vendors.csv vendor-review.json
```

The output must be a new filename. It contains every parsed CSV record, its original values, a decision and reason, any proposed missing fields, and the API result with its provenance. Records without an IBAN remain visible. The script prints only category counts and creates the output with access restricted to the local user on systems that support Unix permissions. The JSON contains the original business data: keep it with the source file, not in a public repository.

## What the example checks before writing

Requests contain at most 100 IBANs, the endpoint's current limit. For each response, the script verifies both the result count and the IBAN at each position. A short or reordered response stops the run, rather than silently attaching bank details to the wrong supplier.

An HTTP error, timeout or incoherent response stops the run without producing a review file. It does not retry or buy credits. Earlier successful batches may already have consumed allowance: inspect the cause before restarting the entire file. Review records stay in input order, including repeated IBANs belonging to separate records.

## Allowance and the first sample

The batch endpoint requires an API key or a supported payment mechanism. This example uses a key and consumes one request or prepaid credit per IBAN submitted. The available allowance depends on that key; the keyless single-IBAN trial does not apply to a batch. Check the current [key options](/docs/onboarding) and [prices](/pricing) before choosing the sample size.

For an integration pilot, include the cases your importer must handle: a missing BIC, an existing BIC, a malformed IBAN and an unavailable lookup. Agree on the review and import rules before expanding to the full file.

## Where this workflow stops

IBANforge does not confirm that an account exists, is open or belongs to the named supplier. A bank's name and address are not the supplier's identity or address. `checks.account_exists` and `checks.payee_name` remain `not_checked`; [Verification of Payee](/docs/vop) is a separate name-to-account service, not part of this import recipe.
