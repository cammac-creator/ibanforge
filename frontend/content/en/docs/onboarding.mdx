# Onboarding: from the first call to the first batch

This guide uses two documentation IBANs: a structurally valid example and a version with an incorrect checksum. They are not beneficiaries to pay. You can also inspect a response in the [playground](/playground) before preparing an integration.

## 1. Inspect a response without a key

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/iban/validate \
  --header 'Content-Type: application/json' \
  --data '{"iban":"CH10 0023 0000 0000 1234 5"}'
```

The REST trial allows **25 validations per ISO week in UTC, per source address**, on `POST /v1/iban/validate` only. The `trial` block reports the remaining allowance and its reset on Monday at 00:00 UTC. A shared network may already have used that allowance: `402` with `cause.reason: "trial_exhausted"` means the trial is exhausted, not that the IBAN is incorrect.

Read the HTTP status first, then the body. A processed request returns `200` even when the IBAN is invalid. This is an **excerpt** of the response obtained for this example on 4 November 2026; other checks and references are omitted:

```json
{
  "iban": "CH1000230000000012345",
  "valid": true,
  "checks": {
    "iban_structure": "pass",
    "iban_checksum": "pass",
    "account_exists": "not_checked",
    "payee_name": "not_checked"
  }
}
```

`valid: true` confirms neither account existence nor its holder. Checks marked `not_checked` have not been performed. A bank-data validation does not authorize a payment.

## 2. Create a key once and keep it

To use batches or keep your own allowance, create a key without an email address:

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/keys/generate
```

A `201` response provides `api_key`, `key_prefix`, `tier` and `monthly_limit`. **Store `api_key` in your application's secret manager**: the full value is shown only once. Also read any `notice`, which explains a reduced allowance during a signup alert. A key without an address normally starts with 25 monthly requests. Claiming it with an emailed code grants 200 requests per month.

Configure your environment to supply that secret as `IBANFORGE_API_KEY`, then reuse the same key:

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/iban/validate \
  --header 'Content-Type: application/json' \
  --header "Authorization: Bearer ${IBANFORGE_API_KEY:?}" \
  --data '{"iban":"CH10 0023 0000 0000 1234 5"}'
```

`X-API-Key` is also accepted. Keep the key out of URLs, shared files and logs. Do not create a key on every run: key-creation limits are separate from the usage allowance. Authenticated responses expose counters in `X-Quota-Used`, `X-Quota-Limit`, `X-Quota-Remaining` and `X-Quota-Month`.

`GET /v1/demo` serves public examples: a successful response does not prove that your key works. Use an authenticated validation for that check.

## 3. Decide what the result establishes

| Field | What to read |
|---|---|
| `valid`, `error`, `error_detail` | The validation verdict and the stated reason when invalid. Keep this separate from an HTTP or network failure. |
| `checks` | Checks performed, failed or not performed. Do not turn `not_checked` into a pass. |
| `bank_code_check` | Bank-code status, consulted register, authority and date. An unknown result or unavailable source needs review; a miss in a partial register does not prove an unallocated code. |
| `bic` | The institution reference when resolved, with provenance. A bank name is not an account-holder name. |
| `sepa`, `risk_indicators` | Coverage and scope indicators. A bank's participation in a scheme does not confirm the beneficiary's identity. |
| `next_steps` | Suggested actions to interpret according to your needs and permissions, not instructions to purchase or pay. |

Invalid responses and different countries do not all include the same blocks. Handle missing fields and `null` values; follow the [validation reference](/docs/iban-validate) and [data sources](/docs/data-sources). Account-holder matching belongs to the bank's [Verification of Payee](/docs/vop) process.

## 4. Try a small batch

The second entry below changes only the check digits and should return an invalid verdict. The JSON body is complete, with no filler entry to replace.

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/iban/batch \
  --header 'Content-Type: application/json' \
  --header "Authorization: Bearer ${IBANFORGE_API_KEY:?}" \
  --data '{"ibans":["CH1000230000000012345","CH1100230000000012345"]}'
```

A batch accepts up to 100 IBANs and consumes **one allowance unit per IBAN**. Start with these two entries: a batch of 100 exceeds an anonymous key's initial allowance. If the remaining allowance is insufficient, the entire batch is refused with `402`.

The response includes `results`, `count` and `valid_count`. Check the HTTP status, result count and each normalized IBAN against the input at the same index. Keep original data and proposals in separate fields; a service failure must not produce a file treated as approved. Reference: [batch validation](/docs/iban-batch).

## 5. Claim the same key if needed

After at least one validation with this key, `POST /v1/keys/claim` accepts your email address in a JSON body, with the key in the `Authorization` header. Without a code, a `202` response with `status: "code_sent"` announces that a code was sent. Repeat the request with the same key, the same address and the received code within 15 minutes. A `200` response with `claimed: true` confirms the claim; the key stays the same.

`403 unused_key` means you must use the key first. An address alone does not complete a claim. An agent sends an address only if its user has authorized that use.

You can also provide an address when calling `POST /v1/keys/generate`. Depending on the network's key-creation history, the service may return `201` immediately or request a code with `403 verification_required`. Read `monthly_limit` and `notice` in the final response. [API Keys](/docs/api-keys) explains these paths and their refusal codes.

## 6. Handle refusals and choose the next step

| Response | Action |
|---|---|
| `200` with `valid: false` | Correct or confirm the input; do not repeat the unchanged call in a loop. |
| `400` | Read the error code and correct the request body or supplied address. |
| `401` | Check the key and its header; do not automatically create a replacement key. |
| `403` | Read the reason: unused key, required verification or incorrect code, depending on the route. |
| `402` | Review the allowance and options. Wait, claim the key if eligible, or select an offer with the responsible person's authorization. |
| `429` | Respect the stated limit and `Retry-After` when present; do not rotate keys or network addresses. |
| Network error or `5xx` | Keep the batch pending and use bounded retries without marking bank details as validated. |

The [error reference](/docs/errors) explains the codes. A `402` or a `next_steps` field does not authorize a credit purchase.
