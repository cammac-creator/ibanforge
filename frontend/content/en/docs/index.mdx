# IBANforge API

IBANforge checks **IBAN structure** and looks up **available bank references**: the bank, BIC and source of the information. Results distinguish a confirmed code, a code absent from a register that supports a conclusion, and insufficient or unavailable reference data. [Coverage by source](/docs/data-sources) explains those differences.

[Download the Postman getting-started collection](/integrations/ibanforge-postman-premiers-appels-4036d71e6896.json)

The service confirms neither account existence nor the account holder. Sanctions indicators concern the institution and country, not the named payee. A valid response is not payment authorisation.

## First call without a key

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/iban/validate \
  --header 'Content-Type: application/json' \
  --data '{"iban":"CH10 0023 0000 0000 1234 5"}'
```

This IBAN is a documentation example, not a payment instruction. The REST trial serves **25 validations per ISO UTC week per source address**, on this route only. The `trial` response states the remaining allowance and reset time. On a shared network, that allowance may already be used; `402 trial_exhausted` is not an IBAN finding.

## Read the result at several levels

- **HTTP**: was the request processed? A quota refusal is not an invalid IBAN.
- **`valid` and `checks`**: format, checksum and checks actually performed. `not_checked` is not `pass`.
- **`bank_code_check` and `bic`**: register finding, authority, source and date. Absence from a partial source does not prove that a code is unallocated.
- **Account limits**: these bank references do not verify account existence, ownership or payee sanctions.

The [validation reference](/docs/iban-validate) explains the fields; the [error reference](/docs/errors) explains refusals. Keep original bank details separate from proposals in your integration.

## Main routes

HTTPS base: `https://api.ibanforge.com`. The complete contract is available in the [OpenAPI reference](/openapi) and [Postman collection](/ibanforge-postman.json).

| Route | Purpose | Access |
|---|---|---|
| `POST /v1/iban/validate` | Structure and references for one IBAN | Keyless trial on this route, then a key or authorised paid access |
| `POST /v1/iban/batch` | Up to 100 IBANs, one result per input | One quota unit per IBAN |
| `GET /v1/bic/:code` | BIC lookup | Key or authorised paid access |
| `GET /v1/ch/clearing/:iid` | Swiss clearing reference | Key or authorised paid access |
| `POST /v1/iban/compliance` | Institution and country indicators | Key or authorised paid access; no payee screening |
| `GET` or `POST /v1/iban/format` | Structure and checksum without bank lookup | Free, no key |
| `GET` or `POST /v1/reference/validate` | Checksum of supported payment references | Free, no key |
| `POST /v1/address/check` | Address format under the requested scheme and its sourced rules | Free, no key |
| `POST /v1/ch/qr-bill/check` | Swiss QR-bill payload structure | Free, no key |
| `POST /v1/audit/upload` | CSV or Excel file review | Free preview; full report at the displayed price |
| `GET /v1/demo` | Public response examples | Free; does not test a key |
| `GET /health` | Public service status | Free |

[Pricing](/pricing) and [access limits](/docs/api-keys) describe the plans. A `402` response explains available options; it does not give an automation permission to buy credits or make a payment.
