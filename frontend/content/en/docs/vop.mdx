# The VoP register and payee verification

IBANforge reports what available sources say about the **resolved bank**. It does not ask that bank to match a payee name against the IBAN. It confirms neither the account’s existence, its holder nor the success of a transfer.

In the [EPC Verification of Payee scheme](https://www.europeanpaymentscouncil.eu/what-we-do/other-schemes/verification-payee-vop), the name check runs between payment service providers. Your PSP’s result remains separate from IBANforge’s indicators.

## Fields to read

When the response to `POST /v1/iban/validate` includes a `sepa` block:

| Field | What it describes |
|---|---|
| `vop_required` | The country-scope indicator calculated by the API. It proves neither the bank’s participation nor, on its own, its obligations. |
| `vop_participant` | `true` when the resolved bank is active in the consulted register; `false` when it is not active; `null` when the result is not established. |
| `vop_register_status` | The detail: `active`, `pending`, `inactive`, `not_listed` or `null`. This field may be absent outside the SEPA area. |
| `register_source`, `register_as_of` | The EPC source and extraction date when an EPC register was read for this bank. |

`bank_code_check.as_of` dates the **bank-code** register, not the VoP register. The presence of `sepa.register_source` does not by itself show that VoP was checked: it can come from another EPC register read for payment schemes.

`risk_indicators.vop_coverage` repeats the country indicator. For the bank’s status, read `sepa.vop_register_status` and `sepa.vop_participant`.

## Interpret the status without inventing a name-check result

| Register status | Useful interpretation |
|---|---|
| `active` | The consulted source lists an active registration. This is neither a real-time availability probe nor a “Match” result. |
| `pending` | Registration pending. Do not treat it as active participation. |
| `inactive` | Inactive registration in the consulted source. No account-holder result. |
| `not_listed` | No status found for the resolved BIC in the consulted register. This does not prove a name mismatch. |
| `null` or missing field | Information not established or field not applicable. This does not mean “No Match”. |

An unresolved BIC, missing register or failed read can produce `null`. Outside the SEPA area, country scope can produce `vop_participant: false` without a VoP-register read. Do not infer from a boolean alone that a register answered.

## First request

Use an example value to inspect the fields; do not send the account holder’s name to this route.

```bash
curl --silent --show-error --fail-with-body \
  https://api.ibanforge.com/v1/iban/validate \
  -H 'Content-Type: application/json' \
  -d '{"iban":"CH1000230000000012345"}'
```

This request can use the keyless validation trial within its available allowance. The [onboarding guide](/docs/onboarding) explains access and retaining a key for an integration. Register values change: this example promises no VoP status for the returned bank. HTTP 200 does not confirm validity or account ownership.

## In an ERP or payment workflow

1. Read `valid` and the `bank_code_check` verdict. Distinguish a format error, an unallocated code and inconclusive information.
2. Retain the VoP status and available source information for review. An active bank can still be unavailable when the real request takes place.
3. If your process needs a name check, use your PSP’s service and retain **its** result: match, close match, no match or verification not possible.
4. Do not turn `false`, `null` or `not_listed` into a name-check result. Do not replace an IBAN or trigger a payment from these indicators alone.

The [EPC](https://www.europeanpaymentscouncil.eu/what-we-do/other-schemes/verification-payee-vop) publishes scheme rules, effective dates and conditions. An IBAN’s country alone does not describe the service your bank actually offers.
