# Recipes: make your first IBAN API call in your language

## Start with a format check, without a key

This free request checks structure and checksum. It sends the documentation example to the API without a bank lookup or key creation:

```bash
curl --silent --show-error --fail-with-body --max-time 15 \
  --get --data-urlencode 'iban=DE89370400440532013000' \
  https://api.ibanforge.com/v1/iban/format
```

For the enrichment examples below, [create a key once](/docs/api-keys), retain it and set `IBANFORGE_API_KEY` in your server environment. Read the actual allowance returned at creation and the usage report; service protections may reduce the initial allowance. Keep the key out of browser code, repositories and spreadsheet cells. [First test](/docs/onboarding) · [Current pricing](/pricing).

Each example makes one validation request and displays the response without deciding a payment. IBANs are sent to the API; use the documentation examples for your trial. An exception stops the script: a network failure, timeout or HTTP 402/429/5xx is not `valid: false`. There is no automatic key creation, purchase or retry.

## Python

Install the official SDK with `python -m pip install ibanforge`, then save this as a Python script:

```python
import json
import os
from ibanforge import IBANforge

key = os.environ.get("IBANFORGE_API_KEY", "").strip()
if not key:
    raise RuntimeError("Set IBANFORGE_API_KEY before this call")

with IBANforge(api_key=key, timeout=15) as client:
    result = client.validate_iban("DE89370400440532013000")
    print(json.dumps(result, ensure_ascii=False, indent=2))
```

For direct HTTP, install `requests` with `python -m pip install requests`. Check the HTTP status before reading a verdict; this output preserves all JSON fields received:

```python
import json
import os
import requests

key = os.environ.get("IBANFORGE_API_KEY", "").strip()
if not key:
    raise RuntimeError("Set IBANFORGE_API_KEY before this call")

response = requests.post(
    "https://api.ibanforge.com/v1/iban/validate",
    json={"iban": "DE89370400440532013000"},
    headers={"Authorization": f"Bearer {key}"},
    timeout=15,
    allow_redirects=False,
)
response.raise_for_status()
if response.status_code != 200:
    raise RuntimeError(f"Unexpected HTTP response: {response.status_code}")
result = response.json()
if not isinstance(result, dict) or not isinstance(result.get("valid"), bool):
    raise RuntimeError("Incomplete validation response")
print(json.dumps(result, ensure_ascii=False, indent=2))
```

SDK HTTP errors derive from `IBANforgeError`; network and timeout failures remain `httpx` exceptions. With `requests`, they derive from `requests.RequestException`. These scripts let failures propagate without printing a false result.

## Node.js / TypeScript

With Node.js 20 or later, save this as `first-call.mjs` and run `node first-call.mjs`. Native `fetch` needs no extra package. The [official TypeScript SDK](https://github.com/cammac-creator/ibanforge/tree/main/sdks/typescript) also provides types and dedicated errors.

```javascript
const key = process.env.IBANFORGE_API_KEY?.trim();
if (!key) throw new Error("Set IBANFORGE_API_KEY before this call");

const response = await fetch("https://api.ibanforge.com/v1/iban/validate", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: `Bearer ${key}`,
  },
  body: JSON.stringify({ iban: "DE89370400440532013000" }),
  signal: AbortSignal.timeout(15_000),
  redirect: "error",
});
if (!response.ok) throw new Error(`HTTP failure: ${response.status}`);
const result = await response.json();
if (!result || typeof result.valid !== "boolean") {
  throw new Error("Incomplete validation response");
}
console.log(JSON.stringify(result, null, 2));
```

## PHP

With PHP 8 or later and the cURL extension enabled, save this as `first-call.php` and run `php first-call.php`. An HTTP failure or incomplete JSON stops the script before it prints a verdict:

```php
<?php
$key = trim(getenv("IBANFORGE_API_KEY") ?: "");
if ($key === "" || str_contains($key, "\r") || str_contains($key, "\n")) {
    throw new RuntimeException("Set IBANFORGE_API_KEY before this call");
}
$request = curl_init("https://api.ibanforge.com/v1/iban/validate");
curl_setopt_array($request, [
    CURLOPT_POST => true,
    CURLOPT_HTTPHEADER => ["Content-Type: application/json", "Authorization: Bearer " . $key],
    CURLOPT_POSTFIELDS => json_encode(["iban" => "DE89370400440532013000"], JSON_THROW_ON_ERROR),
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_FOLLOWLOCATION => false,
    CURLOPT_CONNECTTIMEOUT => 5,
    CURLOPT_TIMEOUT => 15,
]);
$body = curl_exec($request);
$status = curl_getinfo($request, CURLINFO_HTTP_CODE);
if ($body === false) throw new RuntimeException("Network response unavailable");
if ($status !== 200) throw new RuntimeException("HTTP failure: " . $status);
$result = json_decode($body, true, 512, JSON_THROW_ON_ERROR);
if (!is_array($result) || !is_bool($result["valid"] ?? null)) {
    throw new RuntimeException("Incomplete validation response");
}
echo json_encode($result, JSON_PRETTY_PRINT | JSON_THROW_ON_ERROR), PHP_EOL;
```

## Java

With Java 17 or later, add the published SDK 1.8.1 to your Maven project. Jackson is an SDK dependency:

```xml
<dependency>
  <groupId>com.ibanforge</groupId>
  <artifactId>ibanforge-sdk</artifactId>
  <version>1.8.1</version>
</dependency>
```

Save this class as `FirstCall.java` in that project:

```java
import com.ibanforge.sdk.IBANforge;
import com.ibanforge.sdk.model.IBANValidationResult;
import java.time.Duration;

public class FirstCall {
    public static void main(String[] args) {
        String key = System.getenv("IBANFORGE_API_KEY");
        if (key == null || key.isBlank()) {
            throw new IllegalStateException("Set IBANFORGE_API_KEY before this call");
        }
        IBANforge client = IBANforge.builder()
            .apiKey(key.trim()).timeout(Duration.ofSeconds(15)).build();
        IBANValidationResult result = client.validateIban("DE89370400440532013000");
        System.out.println(result.valid());
        System.out.println(result.bic() == null ? null : result.bic().code());
        System.out.println(result.bankCodeCheck());
    }
}
```

A missing BIC prints `null`. `bankCodeCheck()` preserves the fields exposed by this model, including register and date. SDK failures stop the example. This version’s models do not expose every API addition, including some notices and metadata; use an HTTP client when you need the full JSON. [README and methods](https://github.com/cammac-creator/ibanforge/tree/main/sdks/java).

## C# / .NET

In a .NET 8 console project, install the [published 1.8.1 package](https://www.nuget.org/packages/IBANforge.Sdk/1.8.1):

```bash
dotnet add package IBANforge.Sdk --version 1.8.1
```

Replace `Program.cs` with this example:

```csharp
using IBANforge.Sdk;
using System.Text.Json;

var key = Environment.GetEnvironmentVariable("IBANFORGE_API_KEY");
if (string.IsNullOrWhiteSpace(key))
    throw new InvalidOperationException("Set IBANFORGE_API_KEY before this call");

using var client = new IBANforgeClient(new IBANforgeOptions {
    ApiKey = key.Trim(),
    Timeout = TimeSpan.FromSeconds(15),
});
var result = await client.ValidateIbanAsync("DE89370400440532013000");
Console.WriteLine(JsonSerializer.Serialize(new {
    valid = result.Valid,
    bic = result.Bic,
    bank_code_check = result.BankCodeCheck,
}));
```

Missing fields stay `null`; an exception prevents a result from being printed. This output is a subset of the model fields, not the API’s complete JSON. In an existing application you can also pass your own `HttpClient`. [README and model limitations](https://github.com/cammac-creator/ibanforge/tree/main/sdks/dotnet).

## Google Sheets

Use the official functions: they keep the key in your user properties and send columns in batches, without putting a key in a cell.

1. [Download the three Apps Script files](/integrations/ibanforge-sheets-5cbf91ae9bd2.zip) and unzip them. In a test spreadsheet, open **Extensions → Apps Script**.
2. Replace `Code.gs`, add an HTML file named `Sidebar` and paste `Sidebar.html`. In project settings, show `appsscript.json` and replace its content with the supplied manifest. Save.
3. Run `ibfShowSidebar` in the editor and authorize the script. Return to the spreadsheet and save your key in the sidebar, never in a cell.
4. [Import these two test IBANs into column A](/integrations/ibanforge-exemples-e69b509f4ab1.csv) through **File → Import**. They are a public documentation example and its invalid-checksum variant, not accounts to pay. Enter `=IBAN_CHECK(A2:A3)` in B2 and leave five columns empty.
5. Check both rows: `TRUE` for the first format, `FALSE` for the second. Then read bank, BIC, bank-code verdict and SEPA. Missing fields are not payment approval.

Two IBANs consume two quota units, not one billable call. Cached results may avoid a new request for six hours; cache retention is not guaranteed. **Manual installation**; this download is not a Google Workspace Marketplace listing. [All functions and limits](/sheets).

## n8n

### First test on n8n Cloud or self-hosted n8n

1. [Download the workflow JSON](/integrations/ibanforge-n8n-52a8fcab22ed.json) and choose **Import from File** in the n8n workflow menu. It only contains two built-in nodes: Manual Trigger and HTTP Request. No extension or key is included.
2. Open **Contrôler l’exemple de documentation**: POST to `/v1/iban/validate`, JSON body with public example `DE89370400440532013000`. Execute manually once.
3. Check that output contains `valid`, `bank_code_check` and available sources. The workflow performs no payment or downstream action. HTTP errors, exhausted quota and timeouts stop the step.
4. For your own key quota, choose **Generic Credential Type → Header Auth** in the HTTP node: name `Authorization`, value `Bearer ` followed by your key. Store the key in credentials, never in exported JSON.

The keyless test uses the REST allowance described in the [onboarding guide](/docs/onboarding), shared by network address. n8n Cloud users may share an address; configure your key if its allowance is exhausted. [Import a workflow](https://docs.n8n.io/workflows/export-import/) · [HTTP Request options](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest/).

### Review a supplier batch before an ERP import

[Download the review workflow](/integrations/ibanforge-n8n-revue-cf41a091e3a7.json) to preserve the original rows and produce a JSON findings file. It uses built-in nodes and an API key, without a community extension. Import and execution were verified with **n8n 2.46.6**; node names and canvas notes are in French. Execution on n8n Cloud has not been tested.

1. Import the file into a new workflow. In **Contrôler les IBAN avec la clé**, select a **Header Auth** credential: `Authorization`, then `Bearer ` followed by your [API key](/docs/api-keys). Never put the key in exported workflow JSON.
2. Run the four fictional sample rows. They illustrate incorrect IBANs, a row without an IBAN and a duplicate; they represent no real supplier.
3. In **Télécharger la revue JSON**, open the **Binary** output, field `data`, to save the file. The preceding node shows findings for each row.
4. For your data, replace **Lignes fictives à remplacer** with a JSON source of **1 to 100 rows**, with `iban` as text. `bic` and `bank_name` are optional; other columns remain in `original`.

Proposals stay in `review.proposal`, separate from the original values. `ask_supplier` reports a specific anomaly; `review` preserves uncertainty, missing fields or duplicates; `enrichment_proposal` contains only proposed fields with their references. An unidentified bank never becomes a verified result. No status authorises a payment.

Only IBANs are sent to the API. The batch uses [one quota unit per IBAN](/docs/iban-batch), including duplicates. HTTP errors, exhausted quota and inconsistent responses stop the workflow without a new file, automatic retry or purchase. Rows without IBANs are retained for review without an API call. Original data and reports remain in n8n and its execution history: configure retention before using real data.

### Community extension for self-hosted n8n

The published package [`n8n-nodes-ibanforge@0.1.3`](https://www.npmjs.com/package/n8n-nodes-ibanforge) supports IBAN validation, BIC lookup, Swiss clearing and bank-level compliance pre-checks. This recipe is for **self-hosted n8n**, with an owner or admin account. Installing a package from npm is not available on n8n Cloud; Cloud requires a verified listing. See [n8n's installation guide](https://docs.n8n.io/integrations/community-nodes/installation-and-management/).

1. Open **Settings → Community nodes → Install** and enter `n8n-nodes-ibanforge@0.1.3`.
2. Get a [free API key](/docs/api-keys) (25 requests/month without email, 200 after claiming, no card). In a new workflow, connect **Manual Trigger** to **IBANforge** and paste the key into an **IBANforge API** credential.
3. Select **Validate IBAN**, enter the documentation example `DE89370400440532013000`, then execute the step.
4. Inspect the JSON output: `valid` should be `true` for this example, `bank_code_check` reports the register result, and `bic` identifies the bank when available. A completed operation returning these fields proves the first API call; a green credential test alone does not.

In version 0.1.3, the credential test calls the public `/v1/demo` endpoint, which does not verify the key. Check the actual **Validate IBAN** result before using the workflow. Neither format validity nor a bank match proves that the account exists or belongs to a named beneficiary.

For a manual installation, run the following **as the n8n service user**, inside its container if applicable, then restart n8n:

```bash
mkdir -p ~/.n8n/nodes
cd ~/.n8n/nodes
npm install n8n-nodes-ibanforge@0.1.3
```

The node handles each incoming item separately; it has no batch operation. A list of 100 items can therefore consume 100 requests. [Manual installation details](https://docs.n8n.io/integrations/community-nodes/installation-and-management/manual-installation/).

## Odoo

The [public Odoo module](https://github.com/cammac-creator/ibanforge-odoo/tree/18.0), version **18.0.1.0.0** (AGPL-3), fills the BIC and bank name when the API can resolve them. It requires **Odoo 18 with support for custom Python modules**, on your own server or Odoo.sh. [Odoo Online does not support these modules](https://www.odoo.com/documentation/18.0/administration/odoo_online.html). This installation uses the source repository and does not depend on an Odoo Apps listing.

On your own Odoo server, clone the repository into a directory of your choice:

```bash
git clone --branch 18.0 --single-branch https://github.com/cammac-creator/ibanforge-odoo.git /path/to/ibanforge-odoo
```

Add `/path/to/ibanforge-odoo` to Odoo's existing `addons_path` list, keeping the other entries. The module is its **child directory**: the manifest must be at <code className="break-all">/path/to/ibanforge-odoo/ibanforge_bank_autofill/__manifest__.py</code>. Alternatively, copy only that `ibanforge_bank_autofill` directory into an already configured addons directory. Ensure the Python `requests` library is available in Odoo's environment. On Odoo.sh, add that module directory to your project using the [custom-module procedure](https://www.odoo.com/documentation/18.0/administration/odoo_sh/getting_started/create.html).

1. Restart Odoo, enable developer mode and update the apps list. Remove the default **Apps** filter if needed, then install **IBANforge Bank Auto-fill** (`ibanforge_bank_autofill`).
2. Open **Settings → IBANforge**, paste your [API key](/docs/api-keys) and save the settings. Keep the default API address. Without a key, the module makes no network calls.
3. In a test database, create a partner bank account using `DE89370400440532013000`. Leave the bank field empty, enter the IBAN, then leave the field. Check the detected bank/BIC or the linked bank, save, and reopen the account to confirm that the bank link was kept.

An unavailable API or a missing BIC leaves automatic filling inactive; it does not block saving. Odoo's own `base_iban` still validates the IBAN format. At save time, a bank already set on the account is preserved. Entering and saving a new account can use **two API calls**, so 200 monthly requests do not mean 200 manually entered accounts. The IBAN is sent to the configured API; the result does not establish account ownership. [Module behavior and limitations](https://github.com/cammac-creator/ibanforge-odoo/blob/18.0/ibanforge_bank_autofill/README.rst).

## AI agents (MCP)

Remote MCP: add `https://api.ibanforge.com/mcp` in a compatible client. For a local process:

```bash
npx -y ibanforge-mcp
```

Or the hosted transport, no install: `https://api.ibanforge.com/mcp` — it answers 25 free tool calls a week per source address with no key at all (ISO week in UTC, reset on Monday 00:00 UTC), which is the fastest way for an assistant to evaluate the data before you commit to anything. With your key in the `Authorization: Bearer` header, its calls count against that key exactly as on the REST API ([where to put it](/docs/mcp)).

## Read the result before integrating

The bank, BIC, sources and dates depend on the response received. No fixed bank name is required for these recipes to work.

| Field | How to read it |
|---|---|
| `valid` | The IBAN check, separate from the bank-code verdict. An HTTP failure is not an invalid result. |
| `bic` | Bank identification when available; `null` stays unknown. |
| `bank_code_check` | Status, reason, source and date of the reference used. A partial register cannot prove bank absence. |
| `bank_code_holder`, metadata and retirement fields | Additional HTTP response fields; check whether the SDK model version exposes them. |

These checks establish neither account existence nor account ownership. Do not automatically replace supplied banking details. Preserve the response and its provenance in your review workflow, with retention appropriate to your data.
