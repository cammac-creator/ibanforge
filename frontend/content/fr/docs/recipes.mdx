# Recettes : réussir le premier appel IBAN dans votre langage

## Commencer par le format, sans clé

Ce premier appel gratuit vérifie la structure et la somme de contrôle. Il transmet l’exemple de documentation à l’API, sans recherche bancaire et sans créer de clé :

```bash
curl --silent --show-error --fail-with-body --max-time 15 \
  --get --data-urlencode 'iban=DE89370400440532013000' \
  https://api.ibanforge.com/v1/iban/format
```

Pour les exemples avec enrichissement ci-dessous, [créez une clé une seule fois](/fr/docs/api-keys), conservez-la et configurez `IBANFORGE_API_KEY` dans l’environnement de votre serveur. Lisez le quota effectivement renvoyé à la création et le rapport d’usage ; le premier quota peut être réduit par les protections du service. Aucune clé dans le navigateur, le dépôt ou une cellule de tableur. [Premier essai](/fr/docs/onboarding) · [Tarifs actuels](/fr/pricing).

Chaque exemple fait une validation unitaire. Il affiche ce qui a été reçu, sans décider d’un paiement. Les IBAN sont transmis à l’API ; utilisez les exemples documentaires pour l’essai. Une exception arrête le script : une erreur réseau, un délai dépassé ou un HTTP 402/429/5xx ne devient pas `valid: false`. Il n’y a ni nouvelle clé, ni achat, ni relance automatique.

## Python

Avec le SDK officiel, installé par `python -m pip install ibanforge`, enregistrez ce code dans un script Python :

```python
import json
import os
from ibanforge import IBANforge

key = os.environ.get("IBANFORGE_API_KEY", "").strip()
if not key:
    raise RuntimeError("Configurer IBANFORGE_API_KEY avant cet appel")

with IBANforge(api_key=key, timeout=15) as client:
    result = client.validate_iban("DE89370400440532013000")
    print(json.dumps(result, ensure_ascii=False, indent=2))
```

Avec HTTP directement, installez `requests` par `python -m pip install requests`. Vérifiez le statut avant de lire un verdict ; la sortie conserve tous les champs JSON reçus :

```python
import json
import os
import requests

key = os.environ.get("IBANFORGE_API_KEY", "").strip()
if not key:
    raise RuntimeError("Configurer IBANFORGE_API_KEY avant cet appel")

response = requests.post(
    "https://api.ibanforge.com/v1/iban/validate",
    json={"iban": "DE89370400440532013000"},
    headers={"Authorization": f"Bearer {key}"},
    timeout=15,
    allow_redirects=False,
)
response.raise_for_status()
if response.status_code != 200:
    raise RuntimeError(f"Réponse HTTP inattendue : {response.status_code}")
result = response.json()
if not isinstance(result, dict) or not isinstance(result.get("valid"), bool):
    raise RuntimeError("Réponse de validation incomplète")
print(json.dumps(result, ensure_ascii=False, indent=2))
```

Les erreurs HTTP du SDK dérivent de `IBANforgeError` ; les erreurs réseau et de délai restent des exceptions `httpx`. Pour `requests`, elles dérivent de `requests.RequestException`. Le script laisse remonter ces erreurs sans afficher un faux résultat.

## Node.js / TypeScript

Avec Node.js 20 ou plus, enregistrez le code dans `premier-appel.mjs`, puis lancez `node premier-appel.mjs`. `fetch` est intégré ; aucun paquet supplémentaire n’est requis. Le [SDK TypeScript officiel](https://github.com/cammac-creator/ibanforge/tree/main/sdks/typescript) fournit aussi les types et les erreurs dédiées.

```javascript
const key = process.env.IBANFORGE_API_KEY?.trim();
if (!key) throw new Error("Configurer IBANFORGE_API_KEY avant cet appel");

const response = await fetch("https://api.ibanforge.com/v1/iban/validate", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: `Bearer ${key}`,
  },
  body: JSON.stringify({ iban: "DE89370400440532013000" }),
  signal: AbortSignal.timeout(15_000),
  redirect: "error",
});
if (!response.ok) throw new Error(`Échec HTTP : ${response.status}`);
const result = await response.json();
if (!result || typeof result.valid !== "boolean") {
  throw new Error("Réponse de validation incomplète");
}
console.log(JSON.stringify(result, null, 2));
```

## PHP

Avec PHP 8 ou plus et l’extension cURL activée, enregistrez le code dans `premier-appel.php`, puis lancez `php premier-appel.php`. Une réponse HTTP en erreur ou un JSON incomplet interrompt le script avant tout verdict :

```php
<?php
$key = trim(getenv("IBANFORGE_API_KEY") ?: "");
if ($key === "" || str_contains($key, "\r") || str_contains($key, "\n")) {
    throw new RuntimeException("Configurer IBANFORGE_API_KEY avant cet appel");
}
$request = curl_init("https://api.ibanforge.com/v1/iban/validate");
curl_setopt_array($request, [
    CURLOPT_POST => true,
    CURLOPT_HTTPHEADER => ["Content-Type: application/json", "Authorization: Bearer " . $key],
    CURLOPT_POSTFIELDS => json_encode(["iban" => "DE89370400440532013000"], JSON_THROW_ON_ERROR),
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_FOLLOWLOCATION => false,
    CURLOPT_CONNECTTIMEOUT => 5,
    CURLOPT_TIMEOUT => 15,
]);
$body = curl_exec($request);
$status = curl_getinfo($request, CURLINFO_HTTP_CODE);
if ($body === false) throw new RuntimeException("Réponse réseau indisponible");
if ($status !== 200) throw new RuntimeException("Échec HTTP : " . $status);
$result = json_decode($body, true, 512, JSON_THROW_ON_ERROR);
if (!is_array($result) || !is_bool($result["valid"] ?? null)) {
    throw new RuntimeException("Réponse de validation incomplète");
}
echo json_encode($result, JSON_PRETTY_PRINT | JSON_THROW_ON_ERROR), PHP_EOL;
```

## Java

Avec Java 17 ou plus, ajoutez le SDK publié 1.8.1 à votre projet Maven. Jackson est une dépendance du SDK :

```xml
<dependency>
  <groupId>com.ibanforge</groupId>
  <artifactId>ibanforge-sdk</artifactId>
  <version>1.8.1</version>
</dependency>
```

Enregistrez cette classe dans `PremierAppel.java`, au sein du projet :

```java
import com.ibanforge.sdk.IBANforge;
import com.ibanforge.sdk.model.IBANValidationResult;
import java.time.Duration;

public class PremierAppel {
    public static void main(String[] args) {
        String key = System.getenv("IBANFORGE_API_KEY");
        if (key == null || key.isBlank()) {
            throw new IllegalStateException("Configurer IBANFORGE_API_KEY avant cet appel");
        }
        IBANforge client = IBANforge.builder()
            .apiKey(key.trim()).timeout(Duration.ofSeconds(15)).build();
        IBANValidationResult result = client.validateIban("DE89370400440532013000");
        System.out.println(result.valid());
        System.out.println(result.bic() == null ? null : result.bic().code());
        System.out.println(result.bankCodeCheck());
    }
}
```

Le BIC absent est affiché `null`. `bankCodeCheck()` conserve les champs exposés par ce modèle, notamment registre et date. Les erreurs du SDK interrompent l’exemple. Les modèles de cette version n’exposent pas tous les ajouts de l’API, dont certaines notices et métadonnées ; pour conserver le JSON intégral, utilisez un client HTTP. [README et méthodes](https://github.com/cammac-creator/ibanforge/tree/main/sdks/java).

## C# / .NET

Dans un projet console .NET 8, installez le [paquet publié 1.8.1](https://www.nuget.org/packages/IBANforge.Sdk/1.8.1) :

```bash
dotnet add package IBANforge.Sdk --version 1.8.1
```

Remplacez le contenu de `Program.cs` par cet exemple :

```csharp
using IBANforge.Sdk;
using System.Text.Json;

var key = Environment.GetEnvironmentVariable("IBANFORGE_API_KEY");
if (string.IsNullOrWhiteSpace(key))
    throw new InvalidOperationException("Configurer IBANFORGE_API_KEY avant cet appel");

using var client = new IBANforgeClient(new IBANforgeOptions {
    ApiKey = key.Trim(),
    Timeout = TimeSpan.FromSeconds(15),
});
var result = await client.ValidateIbanAsync("DE89370400440532013000");
Console.WriteLine(JsonSerializer.Serialize(new {
    valid = result.Valid,
    bic = result.Bic,
    bank_code_check = result.BankCodeCheck,
}));
```

Les champs absents restent `null`, et une exception empêche la production du résultat. Cette sortie est un sous-ensemble des champs du modèle, pas le JSON intégral de l’API. Pour une application existante, le client accepte aussi votre `HttpClient`. [README et limites des modèles](https://github.com/cammac-creator/ibanforge/tree/main/sdks/dotnet).

## Google Sheets

Utilisez les fonctions officielles qui stockent la clé dans vos propriétés utilisateur et envoient les colonnes par lots, plutôt qu’une clé écrite dans une cellule.

1. [Téléchargez les trois fichiers Apps Script](/integrations/ibanforge-sheets-5cbf91ae9bd2.zip) et décompressez le ZIP. Dans un classeur de test, ouvrez **Extensions → Apps Script**.
2. Remplacez `Code.gs`, ajoutez un fichier HTML nommé `Sidebar`, puis copiez `Sidebar.html`. Dans les paramètres du projet, affichez `appsscript.json` et remplacez son contenu par le manifeste fourni. Enregistrez.
3. Dans l’éditeur, exécutez `ibfShowSidebar` et autorisez le script. Revenez au classeur ; enregistrez votre clé dans la barre latérale. Ne la collez pas dans les cellules.
4. [Importez ces deux IBAN de test en colonne A](/integrations/ibanforge-exemples-e69b509f4ab1.csv) avec **Fichier → Importer**. Ce sont un exemple public de documentation et sa variante à clé invalide, pas des comptes à payer. En B2, saisissez `=IBAN_CONTROLE(A2:A3)` et laissez cinq colonnes libres.
5. Vérifiez les deux lignes : `TRUE` pour le format du premier, `FALSE` pour le second. Lisez ensuite banque, BIC, verdict du code banque et SEPA. Les champs absents ne doivent pas être interprétés comme un accord de paiement.

Deux IBAN représentent deux unités de quota, pas un seul appel facturé. Le cache peut éviter une nouvelle requête pendant six heures, sans garantie de conservation. **Installation manuelle** ; ce téléchargement n’est pas une fiche Google Workspace Marketplace. [Toutes les fonctions et les limites](/fr/sheets).

## n8n

### Premier essai sur n8n Cloud ou auto-hébergé

1. [Téléchargez le workflow JSON](/integrations/ibanforge-n8n-52a8fcab22ed.json), puis utilisez **Import from File** dans le menu du workflow n8n. Il contient uniquement deux nœuds natifs : Manual Trigger et HTTP Request ; aucune extension ni clé n’est incluse.
2. Ouvrez **Contrôler l’exemple de documentation** : POST vers `/v1/iban/validate`, corps JSON avec l’exemple public `DE89370400440532013000`. Exécutez manuellement une fois.
3. Vérifiez que la sortie contient `valid`, `bank_code_check` et les sources disponibles. Le workflow ne lance aucun paiement ni action en aval. Un échec HTTP, un quota épuisé ou un délai dépassé arrête l’étape.
4. Pour conserver un quota sur votre propre clé, choisissez **Generic Credential Type → Header Auth** dans le nœud HTTP : nom `Authorization`, valeur `Bearer ` suivie de votre clé. Gardez la clé dans les credentials, jamais dans le JSON exporté.

L’essai sans clé utilise le quota REST décrit dans le [guide de démarrage](/fr/docs/onboarding), partagé par adresse réseau. Sur n8n Cloud, plusieurs utilisateurs peuvent partager une adresse ; si le quota est épuisé, configurez votre clé. [Importer un workflow](https://docs.n8n.io/workflows/export-import/) · [Paramètres HTTP Request](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest/).

### Revoir un lot fournisseurs avant un import ERP

[Téléchargez le modèle de revue](/integrations/ibanforge-n8n-revue-cf41a091e3a7.json) pour conserver les lignes originales et obtenir un fichier JSON de constats. Il utilise des nœuds intégrés et une clé API, sans extension communautaire. Import et exécution vérifiés avec **n8n 2.46.6** ; les nœuds et les notes sont en français. L’exécution sur n8n Cloud n’a pas été essayée.

1. Importez le fichier dans un nouveau workflow. Dans **Contrôler les IBAN avec la clé**, choisissez un credential **Header Auth** : `Authorization`, puis `Bearer ` suivi de votre [clé API](/fr/docs/api-keys). Ne collez pas la clé dans le workflow exporté.
2. Exécutez les quatre lignes fictives fournies. Elles illustrent des IBAN incorrects, une ligne sans IBAN et un doublon ; elles ne représentent aucun fournisseur réel.
3. Dans **Télécharger la revue JSON**, ouvrez la sortie **Binary**, champ `data`, pour enregistrer le fichier. Le nœud précédent montre les constats par ligne.
4. Pour vos données, remplacez **Lignes fictives à remplacer** par une source JSON de **1 à 100 lignes**, avec une colonne `iban` de type texte. `bic` et `bank_name` sont facultatives ; les autres colonnes restent dans `original`.

Les propositions restent dans `review.proposal`, séparées des valeurs d’origine. `ask_supplier` signale une anomalie précise ; `review` conserve une incertitude, un champ manquant ou un doublon ; `enrichment_proposal` contient seulement des champs proposés avec leurs références. Une banque non identifiée ne devient jamais un résultat validé. Aucun statut n’autorise un paiement.

Seuls les IBAN sont envoyés à l’API. Le lot utilise [une unité de quota par IBAN](/fr/docs/iban-batch), doublons compris. Une erreur HTTP, un quota épuisé ou une réponse incohérente arrête le workflow sans nouveau fichier, sans relance ni achat automatique. Un lot sans IBAN est conservé pour revue sans appel API. Les données originales et le rapport restent dans n8n et son historique : adaptez leur conservation avant d’y placer des données réelles.

### Extension communautaire pour n8n auto-hébergé

Le paquet publié [`n8n-nodes-ibanforge@0.1.3`](https://www.npmjs.com/package/n8n-nodes-ibanforge) propose la validation IBAN, la recherche BIC, le clearing suisse et les pré-contrôles de conformité au niveau bancaire. Cette recette concerne **n8n auto-hébergé**, avec un compte propriétaire ou administrateur. L'installation d'un paquet depuis npm n'est pas disponible sur n8n Cloud, qui exige une fiche vérifiée. Voir le [guide d'installation n8n](https://docs.n8n.io/integrations/community-nodes/installation-and-management/).

1. Ouvrez **Settings → Community nodes → Install** et saisissez `n8n-nodes-ibanforge@0.1.3`.
2. Obtenez une [clé API gratuite](/fr/docs/api-keys) (25 requêtes/mois sans e-mail, 200 après réclamation, sans carte). Dans un nouveau workflow, reliez **Manual Trigger** à **IBANforge** et collez la clé dans un identifiant **IBANforge API**.
3. Choisissez **Validate IBAN**, saisissez l'exemple de documentation `DE89370400440532013000`, puis exécutez l'étape.
4. Lisez le résultat JSON : `valid` doit valoir `true` pour cet exemple, `bank_code_check` décrit le résultat du registre et `bic` la banque lorsqu'elle peut être identifiée. Une opération terminée qui renvoie ces champs prouve le premier appel API ; le seul test de connexion au vert ne suffit pas.

Dans la version 0.1.3, le test de connexion appelle la route publique `/v1/demo`, qui ne vérifie pas la clé. Contrôlez le résultat réel de **Validate IBAN** avant d'utiliser le workflow. Ni un format valide ni une banque identifiée ne prouvent l'existence du compte ou son appartenance à un bénéficiaire nommé.

Pour une installation manuelle, exécutez les commandes suivantes **avec l'utilisateur du service n8n**, dans son conteneur le cas échéant, puis redémarrez n8n :

```bash
mkdir -p ~/.n8n/nodes
cd ~/.n8n/nodes
npm install n8n-nodes-ibanforge@0.1.3
```

Le nœud traite chaque élément entrant séparément ; il n'a pas d'opération batch. Une liste de 100 éléments peut donc consommer 100 requêtes. [Détails de l'installation manuelle](https://docs.n8n.io/integrations/community-nodes/installation-and-management/manual-installation/).

## Odoo

Le [module Odoo public](https://github.com/cammac-creator/ibanforge-odoo/tree/18.0), version **18.0.1.0.0** (AGPL-3), remplit le BIC et le nom de la banque lorsque l'API peut les identifier. Il exige **Odoo 18 avec prise en charge des modules Python personnalisés**, sur votre propre serveur ou sur Odoo.sh. [Odoo Online ne prend pas en charge ces modules](https://www.odoo.com/documentation/18.0/administration/odoo_online.html). Cette installation utilise le dépôt source et ne dépend pas d'une fiche Odoo Apps.

Sur votre propre serveur Odoo, clonez le dépôt dans le répertoire de votre choix :

```bash
git clone --branch 18.0 --single-branch https://github.com/cammac-creator/ibanforge-odoo.git /path/to/ibanforge-odoo
```

Ajoutez `/path/to/ibanforge-odoo` à la liste `addons_path` existante d'Odoo, en conservant les autres chemins. Le module se trouve dans son **sous-répertoire** : le manifeste doit être à <code className="break-all">/path/to/ibanforge-odoo/ibanforge_bank_autofill/__manifest__.py</code>. Vous pouvez aussi copier uniquement ce répertoire `ibanforge_bank_autofill` dans un répertoire d'extensions déjà configuré. Vérifiez que la bibliothèque Python `requests` est disponible dans l'environnement Odoo. Sur Odoo.sh, ajoutez ce répertoire de module à votre projet selon la [procédure des modules personnalisés](https://www.odoo.com/documentation/18.0/administration/odoo_sh/getting_started/create.html).

1. Redémarrez Odoo, activez le mode développeur et actualisez la liste des applications. Retirez le filtre **Apps** par défaut si nécessaire, puis installez **IBANforge Bank Auto-fill** (`ibanforge_bank_autofill`).
2. Ouvrez **Configuration → IBANforge**, collez votre [clé API](/fr/docs/api-keys) et enregistrez les paramètres. Conservez l'adresse API par défaut. Sans clé, le module ne fait aucun appel réseau.
3. Dans une base de test, créez un compte bancaire de partenaire avec `DE89370400440532013000`. Laissez le champ banque vide, saisissez l'IBAN, puis quittez le champ. Contrôlez la banque et le BIC détectés ou la banque associée, enregistrez, puis rouvrez le compte pour vérifier que le lien vers la banque a été conservé.

Une API indisponible ou un BIC absent laisse le remplissage automatique inactif ; cela ne bloque pas l'enregistrement. Le module Odoo `base_iban` continue de valider le format de l'IBAN. À l'enregistrement, une banque déjà indiquée sur le compte est conservée. La saisie puis l'enregistrement d'un nouveau compte peuvent utiliser **deux appels API** : 200 requêtes mensuelles ne représentent donc pas 200 comptes saisis manuellement. L'IBAN est transmis à l'API configurée ; le résultat ne prouve pas la propriété du compte. [Comportement et limites du module](https://github.com/cammac-creator/ibanforge-odoo/blob/18.0/ibanforge_bank_autofill/README.rst).

## Agents IA (MCP)

MCP distant : ajoutez `https://api.ibanforge.com/mcp` dans un client compatible. Pour un processus local :

```bash
npx -y ibanforge-mcp
```

Ou le transport hébergé, sans installation : `https://api.ibanforge.com/mcp` — 25 appels d'outils gratuits par semaine et par adresse source, sans aucune clé (semaine ISO en UTC, remise à zéro le lundi à 00:00 UTC) : le chemin le plus rapide pour qu'un assistant évalue la donnée avant tout engagement. Avec votre clé dans l'en-tête `Authorization: Bearer`, ses appels se comptent sur cette clé exactement comme sur l'API REST ([où la mettre](/docs/mcp)).

## Lire le résultat avant d’intégrer

La banque, le BIC, les sources et leurs dates dépendent de la réponse reçue. Aucun nom bancaire fixe n’est attendu pour réussir ces recettes.

| Champ | Lecture utile |
|---|---|
| `valid` | Résultat du contrôle de l’IBAN, distinct du verdict sur le code banque. Une réponse HTTP en erreur n’est pas un résultat invalide. |
| `bic` | Identification bancaire lorsqu’elle est disponible ; `null` reste inconnu. |
| `bank_code_check` | Statut, motif, source et date de la référence utilisée. Un registre partiel ne prouve pas l’absence d’une banque. |
| `bank_code_holder`, métadonnées et champs de retrait | Informations complémentaires du contrat HTTP ; vérifier leur présence dans la version du modèle SDK utilisée. |

Ces contrôles ne prouvent ni l’existence du compte ni son titulaire. Ne remplacez pas automatiquement des coordonnées fournies. Conservez la réponse et sa provenance dans votre propre parcours de revue, avec une durée de conservation adaptée à vos données.
