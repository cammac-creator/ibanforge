# Prise en main : du premier appel au premier lot

Ce parcours part de deux IBAN documentaires : un exemple de structure valide et sa variante avec une somme de contrôle incorrecte. Ils ne désignent pas des bénéficiaires à payer. Vous pouvez aussi examiner une réponse dans le [playground](/fr/playground), sans préparer d’intégration.

## 1. Examiner une réponse sans clé

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/iban/validate \
  --header 'Content-Type: application/json' \
  --data '{"iban":"CH10 0023 0000 0000 1234 5"}'
```

L’essai REST sert **25 validations par semaine ISO UTC et par adresse source**, sur `POST /v1/iban/validate` uniquement. Le bloc `trial` donne le solde disponible et sa remise à zéro le lundi à 00:00 UTC. Un réseau partagé peut avoir déjà consommé ce solde : `402` avec `cause.reason: "trial_exhausted"` signifie que l’essai est épuisé, pas que l’IBAN est incorrect.

Lisez d’abord le statut HTTP, puis le corps. Une requête traitée répond `200`, même si l’IBAN est invalide. Voici un **extrait** du résultat obtenu pour cet exemple le 4 novembre 2026 ; les autres contrôles et références sont omis :

```json
{
  "iban": "CH1000230000000012345",
  "valid": true,
  "checks": {
    "iban_structure": "pass",
    "iban_checksum": "pass",
    "account_exists": "not_checked",
    "payee_name": "not_checked"
  }
}
```

`valid: true` ne confirme ni l’existence du compte ni son titulaire. Les contrôles `not_checked` restent non effectués. Une validation bancaire n’autorise pas un paiement.

## 2. Créer une clé une fois, puis la conserver

Pour utiliser un lot ou conserver votre propre quota, créez une clé sans e-mail :

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/keys/generate
```

Une réponse `201` fournit `api_key`, `key_prefix`, `tier` et `monthly_limit`. **Conservez `api_key` dans le gestionnaire de secrets de votre application** : la valeur complète n’est affichée qu’une fois. Lisez aussi l’éventuelle `notice`, qui explique un plafond réduit pendant une alerte de création. Une clé sans adresse commence normalement à 25 requêtes mensuelles. Après réclamation par code reçu par e-mail, elle dispose de 200 requêtes par mois.

Configurez votre environnement pour fournir ce secret dans `IBANFORGE_API_KEY`, puis réutilisez la même clé :

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/iban/validate \
  --header 'Content-Type: application/json' \
  --header "Authorization: Bearer ${IBANFORGE_API_KEY:?}" \
  --data '{"iban":"CH10 0023 0000 0000 1234 5"}'
```

`X-API-Key` est également accepté. Ne placez pas la clé dans une URL, un fichier partagé ou un journal. Ne créez pas de clé à chaque lancement : les plafonds de création ne remplacent pas le quota d’utilisation. Les réponses authentifiées indiquent les compteurs dans `X-Quota-Used`, `X-Quota-Limit`, `X-Quota-Remaining` et `X-Quota-Month`.

`GET /v1/demo` sert des exemples publics : son succès ne prouve pas que votre clé fonctionne. Utilisez une validation authentifiée pour ce contrôle.

## 3. Décider ce que le résultat permet de conclure

| Champ | Lecture utile |
|---|---|
| `valid`, `error`, `error_detail` | Verdict de validation et, s’il est invalide, motif indiqué. Séparez-le d’une erreur HTTP ou réseau. |
| `checks` | Contrôles effectués, échoués ou non effectués. Ne transformez pas `not_checked` en réussite. |
| `bank_code_check` | Statut du code bancaire, registre consulté, autorité et date. Un résultat inconnu ou une source indisponible demande une revue ; l’absence dans un registre partiel ne prouve pas un code non attribué. |
| `bic` | Référence de l’établissement quand elle est résolue, avec sa provenance. Le nom de la banque n’est pas le nom du titulaire. |
| `sepa`, `risk_indicators` | Indications de couverture et de portée. La participation d’une banque à un dispositif ne confirme pas l’identité du bénéficiaire. |
| `next_steps` | Suites proposées à interpréter selon votre besoin et vos autorisations, pas un ordre d’achat ou de paiement. |

Les réponses invalides et les pays ne portent pas tous les mêmes blocs. Traitez les champs absents et les valeurs `null` ; suivez la [référence de validation](/fr/docs/iban-validate) et les [sources](/fr/docs/data-sources). Le contrôle du titulaire passe par le circuit bancaire de [Verification of Payee](/fr/docs/vop).


### Référence de la réponse, bloc par bloc

La présence des champs dépend de l’entrée, du pays et des sources réellement consultées. Un verdict invalide précoce peut notamment omettre l’enrichissement. Un bloc absent ou une valeur `null` ne constitue pas un résultat négatif.

| Bloc ou champs | Signification et limites |
|---|---|
| `iban`, `valid`, `error`, `error_detail` | Entrée normalisée, verdict et motif. Un IBAN invalide peut recevoir un statut HTTP `200`. |
| `country`, `check_digits`, `bban`, `formatted` | Pays, chiffres de contrôle, composants nationaux et regroupement lisible, lorsque l’analyse aboutit. |
| `checks` | Contrôles séparés de structure, somme de contrôle, code bancaire et compte national. `account_exists` et `payee_name` restent `not_checked`. |
| `bic` | Établissement résolu avec `source`, `as_of`, `basis` et `authoritative` ; peut porter `lei`, `lei_status`, `address` et `postal_address`. La date d’une source ne prouve pas l’ouverture du compte. |
| `bank_code_check`, `bank_code_holder` | Lire `status`, `reason`, `match`, `register`, `authoritative`, `institution` et `as_of` lorsqu’ils sont fournis. `bank_code_holder` distingue le constat sur le détenteur du code ; une absence dans une source partielle ne prouve pas une non-attribution. |
| `issuer` | Type d’établissement et fondement du classement, lorsqu’il est identifié. Il s’agit de l’établissement, pas du bénéficiaire. |
| `sepa` | `member` décrit le pays. `schemes` et `basis` peuvent décrire une valeur par défaut du pays ou un registre EPC ; lire `bank_reachability` et `bank_schemes` pour la banque. Une donnée bancaire absente ou `null` n’est pas un refus confirmé. |
| `sepa.vop_required`, `risk_indicators.vop_coverage` | Indicateurs de couverture au niveau du pays. Aucun ne contrôle le nom du bénéficiaire. |
| `sepa.vop_participant`, `sepa.vop_register_status` | Participation et statut de l’établissement dans le registre VoP consulté. `null` signifie que la réponse n’a pas pu établir le constat pour cet établissement. Voir la [référence VoP](/fr/docs/vop). Cette réponse de validation ne contient pas de bloc `vop` à la racine. |
| `risk_indicators` | `issuer_type`, `country_risk`, `test_bic`, `sepa_reachable` et `sepa_reachable_scope`, ainsi que `vop_coverage`. Un indicateur du pays ne confirme ni la banque ni le compte. Le score de risque se trouve sur l’[endpoint de conformité](/fr/docs/compliance) distinct. |
| `clearing` | Informations suisses lorsqu’elles sont résolues : `iid`, `sic`, `instant_payments_chf`, `eurosic`, `qr_iid`, `qr_iids` et provenance. Voir le [clearing suisse](/fr/docs/ch-clearing). |
| `pra_authorisation` | Référence d’autorisation britannique lorsqu’elle est trouvée : `firm_name`, `frn`, `section`, `basis`, `source` et `list_month`. L’absence du bloc ne suffit pas à établir qu’une entreprise n’est pas autorisée. |
| `official_identity` | Identité complémentaire issue d’une liste officielle d’établissements en cas de correspondance : `name`, `lei`, `address`, `category`, `matched_by`, `source` et `as_of`. Elle ne change pas le verdict IBAN et n’identifie pas le titulaire du compte. |
| `reference_check` | Constat distinct lorsqu’une référence de paiement est fournie à cette route. Une référence valide ne rend pas valides l’IBAN ou le paiement. Voir les [références de paiement](/fr/docs/swiss-qr-iban). |
| `next_steps` | Suites proposées avec `code`, `do`, `because` et `action`. Appliquer vos autorisations, particulièrement avant un appel payant. |
| `cost_usdc`, `processing_ms` | Coût indiqué et durée de traitement. Cette route de validation indique `cost_usdc: 0` lorsqu’elle répond avec une clé ou sur l’essai REST ; du quota ou des crédits peuvent néanmoins être consommés. |
| `attribution` | Mention de crédit sur les réponses de l’essai sans clé et des clés gratuites. Suivre `required`, `text`, `url` et `note` lorsque les résultats sont montrés à des personnes. |
| `trial` | Compteurs d’une réponse effectivement servie sur l’essai REST sans clé ; absent lorsqu’une clé est utilisée. |

Conserver les champs de source et de date avec les constats enregistrés. Les noms varient selon la source : `bank_code_check` utilise `register`, et le bloc PRA utilise `list_month`. Les [sources de données](/fr/docs/data-sources) détaillent couverture et attribution.

## 4. Tester un petit lot

La seconde entrée ci-dessous change seulement la clé de contrôle : elle doit produire un verdict invalide. Le corps JSON est complet, sans élément de remplissage à remplacer.

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/iban/batch \
  --header 'Content-Type: application/json' \
  --header "Authorization: Bearer ${IBANFORGE_API_KEY:?}" \
  --data '{"ibans":["CH1000230000000012345","CH1100230000000012345"]}'
```

Un lot accepte jusqu’à 100 IBAN et consomme **une unité de quota par IBAN**. Commencez avec ces deux entrées : un lot de 100 dépasse le quota initial d’une clé anonyme. Si le quota disponible ne suffit pas, le lot est refusé en entier avec `402`.

La réponse fournit `results`, `count` et `valid_count`. Vérifiez le statut HTTP, le nombre de résultats et la correspondance de chaque IBAN normalisé avec l’entrée au même index. Conservez les données d’origine et les propositions dans des champs séparés ; une erreur de service ne doit pas produire un fichier considéré comme approuvé. Référence : [validation par lot](/fr/docs/iban-batch).

## 5. Réclamer la même clé si vous le souhaitez

Après au moins une validation avec cette clé, `POST /v1/keys/claim` accepte votre adresse dans un corps JSON, avec la clé dans l’en-tête `Authorization`. Sans code, la réponse `202` et `status: "code_sent"` annoncent l’envoi d’un code. Répétez cette demande avec la même clé, la même adresse et le code reçu dans les 15 minutes. Une réponse `200` avec `claimed: true` confirme la réclamation ; la clé ne change pas.

`403 unused_key` signifie qu’il faut d’abord utiliser la clé. Une adresse seule ne termine pas la réclamation. Un agent ne transmet une adresse que si son utilisateur l’a autorisée pour cet usage.

Vous pouvez aussi fournir une adresse dès `POST /v1/keys/generate`. Selon l’historique de création du réseau, le service peut répondre directement `201` ou demander un code par `403 verification_required`. Lisez `monthly_limit` et `notice` dans la réponse finale. Le détail de ces voies et des refus se trouve dans [Clés API](/fr/docs/api-keys).

## 6. Traiter les refus et choisir la suite

| Réponse | Action |
|---|---|
| `200` avec `valid: false` | Corriger la donnée ou demander sa confirmation ; ne pas répéter le même appel en boucle. |
| `400` | Lire le code d’erreur et corriger le corps ou l’adresse fournie. |
| `401` | Vérifier la clé et son en-tête ; ne pas générer une nouvelle clé automatiquement. |
| `403` | Lire le motif : clé encore inutilisée, vérification nécessaire ou code incorrect selon la route. |
| `402` | Examiner le quota et les options. Attendre, réclamer la clé si elle y est éligible, ou choisir une offre avec l’autorisation de la personne responsable. |
| `429` | Respecter la limite indiquée et, s’il est présent, `Retry-After` ; pas de rotation de clés ou d’adresses réseau. |
| Erreur réseau ou `5xx` | Garder le lot en attente ; prévoir des reprises bornées, sans marquer les coordonnées comme validées. |

La [référence des erreurs](/fr/docs/errors) précise les codes. Un `402` ou un champ `next_steps` ne donne pas l’autorisation d’acheter des crédits.
