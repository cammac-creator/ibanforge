# Erste Schritte: vom ersten Aufruf zum ersten Batch

Diese Anleitung verwendet zwei Dokumentations-IBANs: ein strukturell gültiges Beispiel und eine Variante mit falscher Prüfsumme. Sie bezeichnen keine Zahlungsempfänger. Im [Playground](/de/playground) können Sie eine Antwort auch ohne vorbereitete Integration ansehen.

## 1. Eine Antwort ohne Schlüssel ansehen

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/iban/validate \
  --header 'Content-Type: application/json' \
  --data '{"iban":"CH10 0023 0000 0000 1234 5"}'
```

Der REST-Test erlaubt **25 Validierungen pro ISO-Woche in UTC und Quelladresse**, ausschliesslich auf `POST /v1/iban/validate`. Der Block `trial` nennt das verbleibende Kontingent und die Rücksetzung am Montag um 00:00 UTC. In einem gemeinsam genutzten Netzwerk kann das Kontingent bereits verbraucht sein: `402` mit `cause.reason: "trial_exhausted"` bezeichnet ein erschöpftes Testkontingent, keine falsche IBAN.

Lesen Sie zuerst den HTTP-Status, dann den Inhalt. Eine bearbeitete Anfrage liefert `200`, auch bei einer ungültigen IBAN. Dieser **Auszug** stammt aus der Antwort für das Beispiel vom 4. November 2026; weitere Prüfungen und Referenzen sind ausgelassen:

```json
{
  "iban": "CH1000230000000012345",
  "valid": true,
  "checks": {
    "iban_structure": "pass",
    "iban_checksum": "pass",
    "account_exists": "not_checked",
    "payee_name": "not_checked"
  }
}
```

`valid: true` bestätigt weder die Existenz des Kontos noch dessen Inhaber. Mit `not_checked` markierte Prüfungen wurden nicht durchgeführt. Eine Prüfung von Bankdaten erteilt keine Zahlungsfreigabe.

## 2. Einen Schlüssel einmal erstellen und behalten

Für Batches oder ein eigenes Kontingent erstellen Sie einen Schlüssel ohne E-Mail-Adresse:

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/keys/generate
```

Eine Antwort mit `201` enthält `api_key`, `key_prefix`, `tier` und `monthly_limit`. **Speichern Sie `api_key` in der Geheimnisverwaltung Ihrer Anwendung**: Der vollständige Wert wird nur einmal angezeigt. Lesen Sie auch eine etwaige `notice`, die ein reduziertes Kontingent während eines Anmeldealarms erklärt. Ein Schlüssel ohne Adresse beginnt normalerweise mit 25 monatlichen Anfragen. Nach der Beanspruchung per E-Mail-Code stehen 200 Anfragen pro Monat zur Verfügung.

Stellen Sie das Geheimnis in Ihrer Umgebung als `IBANFORGE_API_KEY` bereit und verwenden Sie denselben Schlüssel weiter:

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/iban/validate \
  --header 'Content-Type: application/json' \
  --header "Authorization: Bearer ${IBANFORGE_API_KEY:?}" \
  --data '{"iban":"CH10 0023 0000 0000 1234 5"}'
```

`X-API-Key` wird ebenfalls akzeptiert. Schlüssel gehören nicht in URLs, gemeinsam genutzte Dateien oder Protokolle. Erstellen Sie nicht bei jedem Start einen neuen Schlüssel: Erstellungsgrenzen und Nutzungskontingent sind getrennt. Authentifizierte Antworten nennen die Zähler in `X-Quota-Used`, `X-Quota-Limit`, `X-Quota-Remaining` und `X-Quota-Month`.

`GET /v1/demo` liefert öffentliche Beispiele: Eine erfolgreiche Antwort beweist nicht, dass Ihr Schlüssel funktioniert. Verwenden Sie dafür eine authentifizierte Validierung.

## 3. Die Aussagekraft des Ergebnisses beurteilen

| Feld | Bedeutung |
|---|---|
| `valid`, `error`, `error_detail` | Validierungsergebnis und angegebener Grund bei einer ungültigen IBAN. Von HTTP- oder Netzwerkfehlern unterscheiden. |
| `checks` | Durchgeführte, fehlgeschlagene oder nicht durchgeführte Prüfungen. `not_checked` heisst: nicht geprüft. |
| `bank_code_check` | Status der Bankkennung, abgefragtes Register, Verbindlichkeit und Datum. Ein unbekanntes Ergebnis oder eine nicht verfügbare Quelle erfordert Prüfung; ein fehlender Eintrag in einem Teilregister beweist keine unzugeteilte Kennung. |
| `bic` | Referenz des ermittelten Instituts samt Herkunft. Der Bankname ist nicht der Name des Kontoinhabers. |
| `sepa`, `risk_indicators` | Angaben zu Abdeckung und Geltungsbereich. Die Teilnahme einer Bank an einem Verfahren bestätigt nicht die Identität des Empfängers. |
| `next_steps` | Vorschläge, die anhand Ihres Bedarfs und Ihrer Berechtigungen einzuordnen sind, keine Kauf- oder Zahlungsaufträge. |

Ungültige Antworten und unterschiedliche Länder enthalten nicht immer dieselben Blöcke. Behandeln Sie fehlende Felder und `null`-Werte gemäss [Validierungsreferenz](/de/docs/iban-validate) und [Datenquellen](/de/docs/data-sources). Der Abgleich mit dem Kontoinhaber gehört zum bankseitigen Verfahren [Verification of Payee](/de/docs/vop).

## 4. Einen kleinen Batch testen

Der zweite Eintrag ändert nur die Prüfziffern und sollte ein ungültiges Ergebnis liefern. Der JSON-Inhalt ist vollständig und enthält keinen zu ersetzenden Fülleintrag.

```bash
curl --silent --show-error --include \
  --request POST https://api.ibanforge.com/v1/iban/batch \
  --header 'Content-Type: application/json' \
  --header "Authorization: Bearer ${IBANFORGE_API_KEY:?}" \
  --data '{"ibans":["CH1000230000000012345","CH1100230000000012345"]}'
```

Ein Batch nimmt bis zu 100 IBANs an und verbraucht **eine Kontingenteinheit pro IBAN**. Beginnen Sie mit diesen zwei Einträgen: Ein Batch von 100 übersteigt das Anfangskontingent eines anonymen Schlüssels. Reicht das verfügbare Kontingent nicht aus, wird der gesamte Batch mit `402` abgelehnt.

Die Antwort enthält `results`, `count` und `valid_count`. Prüfen Sie den HTTP-Status, die Anzahl der Ergebnisse und die Übereinstimmung jeder normalisierten IBAN mit der Eingabe am gleichen Index. Bewahren Sie Originaldaten und Vorschläge in getrennten Feldern auf; ein Dienstausfall darf keine als freigegeben behandelte Datei erzeugen. Referenz: [Batch-Validierung](/de/docs/iban-batch).

## 5. Bei Bedarf denselben Schlüssel beanspruchen

Nach mindestens einer Validierung mit diesem Schlüssel nimmt `POST /v1/keys/claim` Ihre E-Mail-Adresse im JSON-Inhalt entgegen, mit dem Schlüssel im `Authorization`-Header. Ohne Code kündigt eine Antwort mit `202` und `status: "code_sent"` den Codeversand an. Wiederholen Sie die Anfrage innerhalb von 15 Minuten mit demselben Schlüssel, derselben Adresse und dem erhaltenen Code. `200` mit `claimed: true` bestätigt die Beanspruchung; der Schlüssel bleibt unverändert.

`403 unused_key` bedeutet, dass Sie den Schlüssel zuerst verwenden müssen. Eine Adresse allein schliesst die Beanspruchung nicht ab. Ein Agent übermittelt eine Adresse nur, wenn sein Nutzer diese Verwendung erlaubt hat.

Sie können eine Adresse auch bei `POST /v1/keys/generate` angeben. Je nach bisheriger Schlüsselerstellung im Netzwerk antwortet der Dienst sofort mit `201` oder verlangt mit `403 verification_required` einen Code. Lesen Sie `monthly_limit` und `notice` in der abschliessenden Antwort. [API-Schlüssel](/de/docs/api-keys) beschreibt diese Wege und die Ablehnungsgründe.

## 6. Ablehnungen behandeln und den nächsten Schritt wählen

| Antwort | Massnahme |
|---|---|
| `200` mit `valid: false` | Eingabe korrigieren oder bestätigen lassen; den unveränderten Aufruf nicht in einer Schleife wiederholen. |
| `400` | Fehlercode lesen und Anfrageinhalt oder angegebene Adresse korrigieren. |
| `401` | Schlüssel und Header prüfen; keinen Ersatzschlüssel automatisch erzeugen. |
| `403` | Grund lesen: unbenutzter Schlüssel, nötige Bestätigung oder falscher Code, je nach Route. |
| `402` | Kontingent und Optionen prüfen. Warten, einen berechtigten Schlüssel beanspruchen oder mit Erlaubnis der verantwortlichen Person ein Angebot wählen. |
| `429` | Genannte Grenze und gegebenenfalls `Retry-After` beachten; keine Rotation von Schlüsseln oder Netzwerkadressen. |
| Netzwerkfehler oder `5xx` | Batch offenhalten und Wiederholungen begrenzen; Bankdaten nicht als validiert markieren. |

Die [Fehlerreferenz](/de/docs/errors) erläutert die Codes. Ein `402` oder das Feld `next_steps` erlaubt keinen Guthabenkauf.
